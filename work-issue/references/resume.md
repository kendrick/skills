# Resume

Read this at Step 0, item 1, before anything else in the run spends a token or writes under RUN_DIR. Row 5 reads a run dir with no branch as a dead run, so a probe taken after `issue.md` is written would archive the issue it just read.

**The world outranks RUN_DIR, and RUN_DIR outranks memory.** git, gh, and herdr are asked first. RUN_DIR answers only what they cannot see — which reports came back, what the reproducer decided, which triage rows were written. Memory answers nothing: the conversation's account of where the run got to is the one source that was not there when the run actually stopped, and a crashed session's last confident sentence is exactly the sentence to distrust.

`run-state.py probe` prints every field below, `null` where it could not answer, with one `run-state: probe: <field>: <why>` line on stderr for each such field. `phase` exits 3 on a probe missing a field rather than defaulting it, because a field silently defaulting to `false` reads as "no branch yet" and sends a run that is three steps in back to Step 0. A `null` is treated the same way for every field but `pr_state` and `review_state`, where null means no pull request yet: the script answers `stop` naming the field, because a null read as "no" is the same wrong answer arriving through the front door. Row 1 is checked first, since a merged or closed pull request ends the run whatever else the probe could not see.

A `base_sha_state` of `not-merge-base` or `not-ancestor` answers `stop` naming the mismatch, after rows 1 through 3 and ahead of every other row, unless `conflict` or `rebase_in_progress` is true. Step 5 item 2 rewrites `base_sha` after every proven rebase, so a file that has drifted from the live merge-base is a rebase the run never recorded, and every later review would diff against a base the branch has left: on cambium #78 that was four other merged pull requests. Row 12's state is the exception, because a rebase stopped on a conflict or finished by hand is the one the run is about to record, and row 12 sends it back through Step 5 item 1 to item 2, which does it. The probe never rewrites the file itself: a manual rebase taken before the red-team would be adopted as reviewed.

## Gather

`run-state.py probe` is the only way to gather the probe. It reads git, RUN_DIR, a saved pull-request bundle, and the herdr state it is handed, and it calls neither `gh` nor `herdr` itself, so the block below asks those two first. Run it in order, from ROOT:

1. Find the pull request: `gh pr list --head issue-N --state all --json number --jq '.[0].number'`. A non-zero exit stops the run, quoting its stderr, because a failed `gh` prints nothing and nothing reads as no pull request, which sends a run with an open one back to Step 5. Empty output is no pull request: skip item 2.
2. Save the pull request's bundle: `bundle="$(mktemp)"`, then `work-issue/scripts/run-state.py review <PR> --save "$bundle"`. A non-zero exit stops the run, quoting its stderr. The bundle goes outside RUN_DIR: written under it, it would create RUN_DIR before the probe reads it, and a fresh issue would read as row 5's dead run. It carries the pull request's `state` beside its review items, so `pr_state` and `review_state` come from one read.
3. Under HERDR, read the `issue-N` agent's state from `herdr agent list`: `working`, `blocked`, `idle`, or `done`, and `absent` where no such agent is listed. Check the command's flags against `herdr agent --help` at run time; the installed binary is the authority. Pass the state as `--herdr-state`. Without HERDR, leave the flag off and the probe reads `absent`. Under `HERDR_ENV=1` with no `--herdr-state`, `probe` exits 3, because a defaulted `absent` skips row 2's wait and dispatches a second agent into a tree one is still working in.
4. Gather the probe and map it:

   ```
   probe="$(mktemp)"
   work-issue/scripts/run-state.py probe --run-dir RUN_DIR --root ROOT --issue N [--pr-bundle "$bundle"] [--herdr-state STATE] > "$probe"
   work-issue/scripts/run-state.py phase --probe "$probe"
   ```

   Pass `--pr-bundle` only where item 2 saved one. `probe` exits 0 with the JSON on stdout, or 3 with nothing on stdout and a `run-state:` line on stderr: a usage error, a bundle it cannot read or one with no `state`, the HERDR case above, or a bundle with no SINCE to score it against. Exit 3 stops the run, quoting that stderr. `phase` prints `phase: <0-8|done|wait|stop> reason: <one line>` and exits 0, or exits 3 on a malformed probe.

The meanings below use four names the probe resolves itself. **TREE** is the worktree that `git -C ROOT worktree list --porcelain` lists on `refs/heads/issue-N`, else ROOT, and every git read runs there. **DEFAULT** is the branch origin's HEAD names, from `git ls-remote --symref origin HEAD`, since the probe never asks `gh`. **SINCE** is SKILL.md's: `RUN_DIR/pushed_at`, else the committer date of `issue-N`'s head. **The newest round** is the triage round with the highest number k, except where a field says by file time.

Dirty owned paths say it did not, since Step 3 commits a wave only after the gate passes. Clean paths say nothing either way: a worker that returned `failed` or `stopped` without touching its owned paths, or after writing only a path it does not own, leaves them clean. Gate evidence comes from the orchestrator. Only it commits, and only after the gate passes, so a commit on the task's paths is the evidence runs from before the marker existed carry, cambium #78 among them. A run that has a `gated/` directory writes markers, and on it only the marker counts, because a commit reads paths, not tasks: `divvy-up` puts two tasks that share a path in different waves, so an earlier wave's commit would pass a later task whose gate never ran. A task whose worker changed nothing leaves no commit, and its marker is what counts it. Row 7 reverts an uncounted task and re-dispatches it, and the re-dispatch runs the gate. Wave, task, and owned paths are the row's first three cells, as the vendored parser reads them. Each cell loses only its leading and trailing whitespace, so `my task` and `docs/my notes.md` keep their inner spaces, and the owned paths split on commas alone. Any other file in `reports/` counts for nothing, which keeps `build-final.json` and the repair reports out. A filename glob counted only the first name, and on cambium #78 it read five committed waves reported under `<task>.json` as 0 of 5 and sent them to row 7's revert. A `git status` or `git log` that fails, a `base_sha` that does not resolve included, gives `null`, which stops the run naming this field |

The third way to go uncounted, a report beside clean paths with no gate evidence, never reaches this count: such a task has no commit on its paths, or that commit would have counted it, so every reported task whose paths are clean is skipped. Only the orchestrator commits, and only a gated wave, so such a task is committed work whose report is missing or whose paths someone changed after the commit, never a half-written wave. Row 7 stops on a count above 0 rather than reverting. A task with an empty `Files owned` cell is skipped, because `git log` with no paths reads every commit. Cells and owned paths are read as `wave_reports` reads them. A missing or empty `base_sha` is `0`: Step 1 writes it before any wave can commit, so there is no committed wave to protect, and row 7's Step 1 leg stays reachable. Row order is the mechanism, not a convenience. Rows 1 through 3 read the world and outrank every RUN_DIR row below them: a pull request somebody closed while the session was away ends the run no matter how much unfinished state is on disk, and an agent still `working` is waited on rather than duplicated by a second dispatch into the same tree.

Rows 4 and 5 are the two shapes of "nothing to resume", and they differ in what they leave behind. Row 5 has a third reading: a RUN_DIR whose `plan.md` carries a `## Waves` table is a run that passed its gate and stopped before Step 1 made the branch, and that resumes at the confirmation rather than being archived, because the table is the gate's own artifact and nothing else could produce it. None of items 4, 6, or 7 write anything durable, so resuming here re-runs all three before the confirmation is re-asked — item 6's cross-run check most of all, since the crash that stranded this run is not the only thing that could have started in the meantime. The yes to the re-asked confirmation rewrites `redteam/mode.txt` with the mode it carried, since item 7's re-derived mode can differ from the one the earlier yes answered. No branch and no RUN_DIR is a fresh issue. A RUN_DIR with no branch anywhere is the wreckage of a run whose branch was deleted — it moves to `closed/` first, because leaving it in place makes the next invocation resume into a tree that no longer has the commits its reports describe.

Row 7 reverts before it re-dispatches. A wave that wrote files and returned no report left work nobody gated, and handing that to a second worker gives it the first one's leftovers to debug on the plan's budget. The revert stops at HEAD: `git checkout HEAD -- <path>` for each tracked path the wave owns, and deletion of each untracked path it created. It never resets and never checks out a commit older than HEAD, because Step 3 commits a wave only after gating it, so every commit is gated work. It runs before WAVE_BASE is re-recorded, because `divvy-up` records WAVE_BASE with `git stash create`, which on a dirty tree captures the leftovers, and a WAVE_BASE taken first keeps exactly what the revert exists to discard. Where `wave_unreported_committed` is above 0, row 7 stops instead: a missing report beside a commit is a disagreement for a human to settle, and a half-written wave leaves no commit. A task with a report but dirty owned paths, or with a report and no gate evidence, is unreported here, since no gate is known to have read it, so row 7 deletes its reports under both names and its `gated/<wave>-<task>` marker before the revert. It leaves the `gated/` directory in place, even empty, since that directory is what tells `wave_reports` the run writes markers. A report and marker left behind would read as reported once the revert cleans the paths, and a session that died before the re-dispatch returned would resume at row 8 with the task unbuilt. Deleting first means a crash between the two steps still leaves the task unreported.

Rows 10, 11, and 16, and row 17's unsettled-review leg, answer the budget stop (see SKILL.md's **Timing**) while `review_over_budget` is true, each reason keeping its `row <n>:` prefix. Row 10's two-failed-rounds stop keeps its own reason, since it already stops.

Row 16 also holds the review round cap (#159), checked ahead of its budget stop, since a capped round starts no review cycle and a budget stop there stranded its replies. Once `triage_rounds` reaches `max_review_rounds`, the newest round is never repaired: triage queued every in-scope row with `review round cap reached (N)`, so the round is all-queued in the sense row 17 means, even though its Scope cells still read in scope and `triage_inscope_rows` still counts them. Row 16 falls through rather than answering Step 8 itself, because a capped round never gets a repair report and the row would match it on every resume. The one exception is a `triage_stop_rows` count above 0, which counts in-scope rows alone, since an out-of-scope `P0` goes to the queue in any round: queueing an in-scope `P0` or `blocking` row ships a known blocker and repairing it breaks the cap, so row 16 stops with a reason naming both and the call goes to a human.
