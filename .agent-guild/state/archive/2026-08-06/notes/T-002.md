# T-002 notes

## What I built

`inbox-to-memory/scripts/migrate-scope.sh`: added two new flags on top of the
existing Tier 1 loop, no second copy of `extract_body`.

- `--tier2-extract <dir>`: for each v1 note (records excluded — Tier 2 is a
  note concept), writes `<dir>/<id>.extract.md` from the same `$work/body`
  the Tier 1 counts already compute, plus appends a skeleton entry
  (`file:`, empty `summary:`, empty `entities: []`) to `<dir>/proposals.yaml`
  for an agent to fill in. Read-only with respect to the scope; refuses to
  combine with `--apply`.
- `--tier2 <proposals-file>`: at apply time, looks up each note by its own
  `id` (via `yq`'s `env()` interpolation, so filenames with slashes/dots
  never need to go through a yq path) in the proposals file's `notes` map.
  If present, refuses (diagnostic `tier2-summary-multiline`) before any write
  if the summary spans lines, refuses (diagnostic `tier2-entity-unsourced`)
  before any write if any entity doesn't appear verbatim in that note's own
  extract (checked with `grep -Fc` against `$work/body`, never `grep -q`),
  and otherwise appends `summary = ...` / `entities.N = ...` lines directly
  into the note's `$work/props` file — not through the `;`-delimited `extras`
  mechanism, since a summary is free prose and would break that split.
  Both refusals `continue` before `render_frontmatter` ever runs, so the note
  stays byte-identical, never partially written.

A note omitted from the proposals file just proceeds through the ordinary
Tier 1 path with no code path change — that's what makes rejection-as-absence
(C-5) and per-file/batched approval (C-4) fall out for free rather than
needing special-casing.

`tests/inbox-to-memory-smoke.sh`: added a "Migration, Tier 2" section (five
throwaway git repos, each isolating one behavior) plus one assertion dropped
into the existing Tier 1 block (a loop over `$mig`'s four already-migrated
files confirming no `^summary:`/`^entities:` line anywhere, since the
existing suite never asserted that).

## Judgment call: proposals file shape

The spec didn't fix a concrete format for the sidecar's proposals file, only
"a proposals file for the scope" filled in by an agent. I keyed it by note
`id` (`notes.<id>.{summary,entities}`) rather than by relative file path,
since ids are already the unambiguous identity the script uses elsewhere
(`id: ${base: -10}`) and sidestep any yq path-quoting question a filename
with a slash and a dot would raise. The extraction skeleton also writes a
`file:` field per entry as a courtesy for whoever fills it in — it's not
read at apply time.
