## Design choices where the spec left room

- **Resolved-record path canonicalization.** Dedup keys on `realpath` of
  each record (per the spec's `/var/folders` vs `/private/var/folders`
  warning), and the path printed in `stamped:`/`skipped:` lines and used for
  sort order is that real path with the scope's own real path prefix
  stripped — i.e., always the scope-relative spelling, regardless of whether
  the caller passed it absolute or relative. This is what makes C-18's
  `grep -c '^stamped: _memory/'` assertion possible; nothing in the contract
  states the print format explicitly, but "sorted by resolved record path"
  reads most naturally as one canonical spelling, and scope-relative is the
  only one that's stable across absolute/relative callers.
- **Skip-reason wording.** Not fully pinned by the contract (only "names its
  generation" / "names its status" / "names both dates" / "names the
  budget" are required). I used: `(no schema key, v1)`, `(status: <x>, not
  accepted)`, `(<candidate> is not later than <existing>)` — this last one
  copied verbatim from the constitution's own C-5 failing-example text,
  which reads like an intentional hint at the expected phrasing — and
  `(last_confirmed insertion would close frontmatter at line N, past the
  20-line budget)`, echoing `lint-scope.sh`'s own `frontmatter-budget`
  message.
- **"Does not parse" validation.** For records, I treat "no closing
  frontmatter fence" (`frontmatter_end` returns 0) as unparseable. For
  notes, "no `date:` key inside the frontmatter block." Neither is exercised
  by name in the eight clauses' harnesses (only nonexistence is), so this is
  a reasonable-faith reading of "does not parse" rather than a tested
  requirement.
- **No `yq` anywhere in this script.** Every read (schema/status/
  last_confirmed/date) and every write (update or insert) is done with
  `awk`/`sed` against the frontmatter block directly, never a full parse-
  reserialize round trip, per the spec's explicit warning about C-7.
- **Insertion anchor.** Computed generically (scan for the last present key
  among `schema body_schema id memory_type title status date effective_from
  effective_to`, insert right after it) rather than hardcoding "after
  `date:`" — the fixture record has neither `effective_from` nor
  `effective_to`, but a record that does carry them would still land in
  contract position.
