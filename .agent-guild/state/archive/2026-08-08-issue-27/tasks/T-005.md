## Spec excerpt

Add a fifth scenario to `_maintenance/inbox-to-memory/EVALS.md`, backed by a new fixture at `tests/fixtures/inbox-to-memory/evals/confirmation-writethrough/`. That path is pinned — the smoke suite, the eval doc, and the checker all have to agree on the string.

Read `EVALS.md` end to end first. Four scenarios are already there and they set the bar: every row binary, every row settleable off the staged copy, and a "without the skill" baseline paragraph saying what a model that never opened `_memory/` would produce instead. Scenario 1 (`contradiction-amend`) is the closest sibling — same phase 2.5 machinery, opposite outcome.

### What the scenario grades

The judgment half of the write-through: deciding that an input **confirms** a claim an `accepted` record already makes, as opposed to merely mentioning the same subject. The mechanical half — writing the date, skipping v1 — is already covered by the smoke suite and is not what this measures.

`inbox-to-memory/SKILL.md` carries the shipped behavior (T-002): phase 2.5 detects confirmations on the contradiction pass, the stamp runs once for the queue after phase 4 without passing the phase 5 gate, and phase 6 names every record stamped and every one the stamper declined.

### The fixture

One transcript in `_inbox/`, prior notes, and **four records**, each doing a different job:

| Record | Why it is there |
| --- | --- |
| `accepted`, v2 | The transcript genuinely confirms it. Stamped. |
| `accepted`, v1 (no `schema` key) | The transcript confirms it too. Must come out byte-identical. |
| `accepted`, v2 | Read at phase 2.5, neither confirmed nor contradicted. **Not** stamped. |
| `proposed` | The transcript confirms it. Not stamped — nothing has agreed to it yet. |

**The third record is the whole point and the easiest to get wrong.** It has to be close enough to the transcript's subject that a model stamping everything it opened would plausibly stamp it. A record about an unrelated system is a straw negative that every model passes. Make the meeting touch its territory without ever restating its claim — someone mentions the system, nobody says the thing the record says.

Give the scope a plausible client, people, and a real conversation, the way `unacknowledged-tension` and `scope-tiers` do. The fixture has to lint clean (`failures: 0`) as a scope.

### The scenario section

Follow the shape of the four above it: fixture name, run-from, prompt, a binary pass table, then the baseline paragraph. The table covers the stamp, the v1 hold, both negative cases, and the absence of any per-record prompt — that last one matters, because the entire feature is that the user is never asked.

For the baseline: a model without the skill never reads `_memory/` before writing, so no record is named anywhere in its output and no date moves. Say what it produces instead, concretely, the way scenario 1 does.

Leave `:12` alone. It says "Four prior notes" about the `unacknowledged-tension` fixture and that is a fact about that fixture, not a count of scenarios.
