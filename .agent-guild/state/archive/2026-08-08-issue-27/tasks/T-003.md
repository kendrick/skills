## Spec excerpt

The skill now writes into `_memory/` without asking. Roughly a dozen passages across the skill's prose describe a world where it never does. Your job is to find all of them and fix the ones that mislead — not to mention the new behavior everywhere it could conceivably go.

`inbox-to-memory/SKILL.md` already carries the feature (T-002): phase 2.5 detects confirmations, phase 6 reports them, and the Operating Rules name the exception. Read those three sections first; they are the account everything else has to stop contradicting.

### The test that decides each passage

For every candidate, in this order:

1. **Would a user who has read only this passage be surprised to find `git status` showing modified files under `_memory/` after a run in which they approved nothing?** If yes, it is incomplete — carry the exception, or narrow the sentence until it stops making the claim.
2. **Is this passage its document's only account of what the skill does to `_memory/` on its own?** If yes, it carries the burden even when question 1 is arguable.

**Literal truth is not the test.** The write-through creates no record and promotes nothing, so nearly every candidate stays literally true, and a test built on truth passes all of them and changes nothing. An earlier draft of the constitution made exactly that mistake and contradicted its own failing example.

Two boundary cases are pre-ruled and you do not get to re-decide them:

- `inbox-to-memory/README.md:74` — "Nothing is ever promoted to memory automatically. Every record requires your explicit per-candidate approval…" — **fails**. It is the README's only statement about automatic writes, it sits in a list of operational caveats a reader takes as exhaustive, and question 1 answers yes.
- `inbox-to-memory/assets/claude-md/_memory.template.md:65` — "Only create record files in `_memory/` after the user reviews…" — **passes unchanged**. It is step 2 of a numbered "How Records Get Created" procedure, plainly about creation, and nobody reads it as an inventory of every write.

### Two documents owe more than the sentence test

- **`references/machine-contracts.md`** states the `last_confirmed` lifecycle in one place: the migrator initializes it to the record's own date, the write-through advances it and never retreats, and a record with no `schema` key never gains it. That last part follows from the document's own generation table, whose first row puts a v1 file outside the frontmatter contract entirely — so say it as a consequence, not as a new rule.
- **`assets/claude-md/_memory.template.md`** accounts for the write-through somewhere in the file. This is the agent-facing conventions doc that ships into every scaffolded `_memory/`, it lists `last_confirmed` as required frontmatter at `:21` with no account of how the value is ever set, and it is what an agent working in a user's scope actually reads. The `:65` pre-ruling above is about that sentence, not about the file.

**That list is a floor, not a boundary, and the sweep that produced it has a predicate baked in.** It searches for passages about approval and about `last_confirmed`. A passage describing what the skill writes, in neither vocabulary, does not appear in it. The immediately prior job in this repo watched its enumeration move from four to eight across three sweeps, every one of which inherited the same predicate from the clause it was auditing. Question the category, not just the results.

### One sentence to correct, handed down from T-002

Separate from the census, and the only edit in this task that does not come from C-11. Fix `inbox-to-memory/SKILL.md:152`, whose closing clause reads:

> so the same inbox produces a different record and a different report depending on which file got read first.

The report half is right. **The record half is false.** A per-input loop would converge on the same stored date anyway, because the monotonic guard refuses any candidate that is not later than what the record already holds — so the final `last_confirmed` value is identical whichever order the inputs came in. What actually differs is the number of writes and the report the user reads. That is still a real reason to batch, and it is the reason C-5 gives; it is just not the reason this sentence gives.

Change the claim to match, keeping the sentence's shape and voice. T-002's worker wrote the surrounding paragraph and it is good — you are correcting one clause inside it, not rewriting the passage.

For the record on why this is yours: T-002's checker of record flagged the sentence as a non-blocking observation and passed the task; the courier lane independently found the same sentence and failed the clause over it. The verdict of record stands, so T-002 is complete — but two independent readers agreeing a shipped sentence is false is not something to leave in a normative document, and you are the next task in that file.
