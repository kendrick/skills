## Spec excerpt

Build one new file: `inbox-to-memory/scripts/stamp-confirmed.sh`. Change nothing else. It is the mechanical half of a feature whose judgment half stays in prose — the skill decides that an inbox file confirms a memory record, and this script writes the date.

**Read the constitution's "The script contract" section first, in full.** It pins the interface, the output format, the two-stage resolution rule, and the stable output order. Then read your eight clauses. The contract is short and everything below assumes it.

### What it does

Given a scope root and one or more `--note <note> <record>...` groups, set `last_confirmed` on each named record to its group's note `date`, and report every record it touched and every one it declined to.

```
bash inbox-to-memory/scripts/stamp-confirmed.sh <scope-root> [--dry-run] \
  --note <note-path> <record-path>... \
  [--note <note-path> <record-path>...]...
```

It is called **once per run of the skill, not once per input** — a run over an inbox of six files makes one invocation carrying up to six groups. That is load-bearing: it is the only reason "a record confirmed twice in one run is stamped once" can be a property of the script rather than of how the caller loops.

### The two things most likely to go wrong

**Resolution is two stages and the order matters.** Stage 1 collapses the groups to one candidate per distinct record, taking the latest note date among the groups naming it, consulting no record state at all. Stage 2 then makes exactly one decision per resolved record, against the six-row branch table in the contract. A record named by a 2025-12-02 group and a 2026-02-17 group, currently at 2026-02-10, resolves to 2026-02-17 and is stamped once — it is *not* skipped for the older group and stamped for the newer one. Two earlier drafts of the constitution got this wrong in opposite directions; C-5 case 3 and C-18 both test it.

**A stamped record differs from its prior self in exactly one line.** Do not round-trip frontmatter through `yq`. The fixture carries `title: 'Billing region and deployment region are not the same boundary'` in single quotes and `related: [clarifies::G2k65qG3Nc]` inline, and a parse-and-reserialize brings both back in a different shape, fails `frontmatter-single-line`, and puts every unrelated line into the user's `git diff`. Edit the line in place. C-7's `diff -r` is exactly one changed line pair or the task fails.

### Environment

The only `bash` here is **3.2.57**, Apple's. No associative arrays, no `mapfile`, no `${var^^}`. Stage 1's keyed max-date dedupe is the obvious job for `declare -A` and cannot use one — parallel indexed arrays or a sorted stream instead. A `declare -A` in the shipped script will not run.

Dedupe by resolved real path, not by string: `mktemp -d` returns `/var/folders/…` while the same file's real path is `/private/var/folders/…`, so the same record named absolutely and relatively differs by more than a prefix.

### Where the pieces already are

- `inbox-to-memory/scripts/lint-scope.sh` and `migrate-scope.sh` are the house style for a script in this skill — read one before writing. `migrate-scope.sh` already inserts `last_confirmed` during migration and carries the record key order at `:25`; the insertion position you need (after `effective_to`, before `source_refs`) is the same contract.
- `tests/fixtures/inbox-to-memory/mixed/` is the scope every harness runs against. It holds one v2 `accepted` record at `last_confirmed: 2026-02-10`, one v1 `accepted` record with no `schema` key, and notes dated 2025-12-02 through 2026-02-17.
- The 20-line frontmatter budget is real and C-6's second half turns on it. A record missing `last_confirmed` carries at most 17 keys and closes on line 19, so insertion alone never overruns — it takes a comment line inside the block, which every template in `assets/records/` has four of.
