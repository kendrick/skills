### C-12 — no new inline token got registered

The feature deliberately ships **no** new token. A confirmation leaves its trace in the phase 6 report and in the record's own `last_confirmed` date, not in a flag in the note. A `[confirms accepted: …]` token would need a grammar row, a lint check, and a ruling on whether it counts as an unpromoted candidate — and it would look like something waiting for a sign-off that by design never comes.

Prove nothing crept in, by diffing the registered inventory across all four files that enumerate token shapes:

```bash
BASE=f027515c9f5487acd4b8d0be973af0e5bc9017d0
inv() {
  for f in inbox-to-memory/SKILL.md inbox-to-memory/references/machine-contracts.md \
           inbox-to-memory/assets/note.template.md inbox-to-memory/scripts/lint-scope.sh; do
    if [ -n "$1" ]; then git show "$1:$f"; else /bin/cat "$f"; fi
  done | /usr/bin/grep -ohE '\[[a-z][a-z0-9 -]*(:|\])' | sort -u
}
diff <(inv "$BASE") <(inv); echo "inventory exit=$?"
```

SKILL.md is in that list on purpose — its own candidate-flag block at `:95-101` is a place a token can be added, and an earlier version of this check missed it. The extraction picks up harmless noise from `lint-scope.sh`'s regex character classes; that is fine, because the assertion is a set difference and identical noise cancels. Use `/bin/cat` — `cat` is aliased to `ccat` in the agent shell.

### If something is broken

Repair it if it is yours to repair — a stray temp directory, a fixture a test forgot to copy, a file outside the allowlist that should not have been touched. If the repair would mean editing another task's deliverable to change its behavior, that is a finding, not a task: report it and stop.

`inbox-to-memory/scripts/lint-scope.sh` is deliberately not in the allowlist. The stamper is the only script this job adds, and the allowlist naming it by filename rather than admitting `scripts/` is the second lock on the frozen-scripts non-goal. If the diff shows `lint-scope.sh` modified, something upstream went wrong and you report it rather than reverting it.

### The base commit moved, and here is why that is not a finding

Both clauses and this task were repointed to `f027515`, which is `HEAD` now.

That is safe here for a reason you should confirm rather than take on trust: the retrofit touched only files under `.agent-guild/state/archive/`, and none of the four files C-12 reads differs between the two commits. Verify it yourself — compare `git show 924f81f:<f>` against `git show f027515:<f>` for all four — and say so in your report.

**Nothing this job produced is committed, and nothing should be.** If `git rev-parse HEAD` is anything other than `f027515c9f5487acd4b8d0be973af0e5bc9017d0`, someone committed the work and both clauses are comparing a tree against itself. Report that rather than working around it.
