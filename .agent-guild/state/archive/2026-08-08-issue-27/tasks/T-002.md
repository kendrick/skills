## Spec excerpt

Edit `inbox-to-memory/SKILL.md` so the skill actually performs the `last_confirmed` write-through, and add one line to `tests/inbox-to-memory-smoke.sh` pinning that it does. Four sections of SKILL.md change. Nothing else in the repo is yours — the surrounding prose in README, references, and assets belongs to T-003, which runs after you.

### The feature, in one paragraph

When an inbox file confirms a claim an `accepted` memory record already makes, the skill stamps that record's `last_confirmed` date **without stopping for approval**, and names every record it touched in the phase 6 verify report. This is the one sanctioned exception to the rule that nothing in `_memory/` gets written without per-item sign-off. It is metadata rather than content, and gating it would put an obviously-yes prompt in front of every input, which trains rubber-stamping and devalues the gate protecting the writes that need protecting.

### What each section has to say

**Phase 2.5 (C-8).** The pass that detects contradictions also detects confirmations. Same pass, same records, same eligibility rule — `status: accepted` only, matching what the section already says at `:69`. Critically: **the same five-body-read budget**. The sentence at `:67` ("Five body reads per input, and the budget binds") is one of the load-bearing sentences in the file, and a second detection pass with its own reads would make it the least true. Do not add a numbered step with its own reads.

**Phase 6 (C-9).** The verify report names every record whose `last_confirmed` was stamped, **and** every record the stamper declined to write, with the reason. The second list is scoped to what the script skipped — v1, non-`accepted`, not-later, over-budget — not to everything phase 2.5 happened to open. The skipped v1 records are the ones a user would otherwise never learn were left behind, and a silent skip reads identically to a record nobody confirmed. "Note any `last_confirmed` updates" is not enough; the report is the only durable trace of a write the user did not approve.

**Operating Rules (C-10).** Add a rule naming the write-through as the sole sanctioned exception to the sign-off gate, with the reasoning above. It has to read as a bounded exception, not a loosening — say what is still gated. Watch the collision: the list already ends with the VTT bullet at `:459` claiming to be "the one sanctioned exception to preserving raw content exactly as captured." Two rules each calling themselves the one exception, four lines apart, must not leave a reader counting exceptions. Each names the rule it excepts.

**The invocation (C-17).** Three things, and only the first two are derived:

1. **One call for the whole queue, never one per input.** Forced: the script takes every `--note` group in a single invocation, and its dedupe is defined over that invocation. A per-input loop cannot satisfy "a record confirmed twice in one run is stamped once." Say so and say why.
2. **No call at all when phase 2.5 found no confirmations.** Also forced: the script errors on an invocation with no group. Most runs confirm nothing. Say it explicitly rather than leaving it to be inferred from an exit code.
3. **The call sits immediately after phase 4, before phase 5.** This is a **convention, not a derivation.** The close of phase 3 works equally well — phase 4 only disposes sources and opens no gate. Two audits caught earlier drafts of this document asserting the boundary was forced when it is not. Name phase 4, say the choice is a convention, and let (1) carry the weight. A worker who invents a load-bearing reason here has written something false.

Show the invocation in SKILL.md's own `<skill-path>` convention, matching `lint-scope.sh` at `:175`, `migrate-scope.sh` at `:347`, and `verify-migration.sh` at `:399`.

### Out of scope

The grammar table, the token-field list, `REGISTERED_TOKENS`, and `note.template.md` all stay as they are, and a token added to SKILL.md's own candidate-flag block at `:95-101` fails C-12 just as surely.

One trap in how C-12 is checked, since T-007 runs it and you will not be there to explain: the inventory extraction greps `\[[a-z][a-z0-9 -]*(:|\])`, which catches any bracketed run of lowercase letters, digits, spaces, and hyphens — not only tokens. So a new markdown link with an all-lowercase label, or a bracketed aside like `[see below]`, registers as a token shape and fails a clause in someone else's task. Existing link labels carrying `/` or `.` are safe.
