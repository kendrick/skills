## Spec excerpt

Six passages across four files state the old behavior as settled contract. Five are made false by T-001's change; the sixth was already false before anyone touched this repo, and is the most important of them.

Read T-001's actual diff first, with `git diff -- inbox-to-memory/scripts/lint-scope.sh`. Do not write these from this description — write them from the code. The whole point of this task is that prose and code stopped agreeing, so a rewrite based on a summary of the change rather than the change itself reproduces the defect one layer up.

Note that T-002 has already landed regression tests in `tests/inbox-to-memory-smoke.sh` by the time you run. Its diff is not yours to describe, but it is also not a conflict — you are not touching that file.

The first sentence is now false. The remaining two are still true and still worth keeping.

This is the comment the issue was filed against, and it is the reason the defect was recognizable as a defect. Its link half describes what the code now does. This one is load-bearing in a way the others are not: it is the opening premise of the argument for migrating at all, and the rest of that section builds on it. The sentence's job is to say that nothing *compels* migration, and that remains true — link checking is not a reason to migrate, since a v1 file passes it as readily as a v2 one. Keep the argument intact and make the parenthetical about the lint accurate. This file is linked from `SKILL.md:344` as the migration spec, so it is read by people deciding whether to run a migration.

Locations 3, 4, and 5 all say "the lint never flags them." All three are now false in exactly one respect, and the correction should be that narrow — a v1 file is still exempt from the token grammar, the anchor rule, the frontmatter contract, and the four derived counts. **6. `inbox-to-memory/references/machine-contracts.md:13-21`**, the generation table and the sentence beneath it:

> Links and derived counts are checked in all three of the rows the lint touches. A link resolving nowhere is broken in any generation, and the migrator computes the counts it writes rather than guessing them.

This is the hardest of the six and the one most worth getting right. Read it beside location 2, the comment at `:441-443` — they are the same sentence in two registers, and the doc version has all the same problems:

- **It was already false, before this job started.** Pre-fix, links are exactly what the lint does *not* check on a v1 file, so this sentence has been stating the contract the code violates. That is the same disagreement the issue is titled after, sitting in the document the comment points at. T-001 makes its links half true for the first time.
- **Its "derived counts" half is false for row one and always was**, which is verbatim the "and counts" defect you are already fixing at location 2. Repairing the comment and leaving this alone keeps the identical error standing one file over.
- **`:7` and `:21` contradict each other today.** One says the lint never flags a v1 file; the other says links are checked in all three rows. If you rewrite `:7` to say only links are checked and leave `:21` claiming links *and derived counts* are checked everywhere, you ship a document that disagrees with itself about counts — and it would pass every check as written.

**The table is part of this location, not background for it.** Its columns are Frontmatter contract and Body grammar, with no column for Links, and row one reads `not checked | not checked`. Leave it as is and the most authoritative artifact in the repo about generations still answers "what does the lint do to a v1 file" with "nothing." Decide how to fix that — a Links column, a footnote, a reworked sentence — and say why in the prose. **Deleting a claim is not repairing it.** Each of the six locations must still tell a reader which checks a v1 file receives. A file that stops stating its own v1 contract is harder to check against next time, not easier, and the next person to touch this code needs the same signpost that let this defect be spotted.
