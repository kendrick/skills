## Spec excerpt

Write `_maintenance/inbox-to-memory/EVALS.md`, the scenario suite for the `inbox-to-memory` skill's judgment-dependent behavior — the behavior no lint can check. This is the job's central deliverable. The staging script and the fixtures already exist; read them before you write a line.

**The precedent is `_maintenance/file-issue/EVALS.md`.** Read it first and follow its shape: an opening method statement, `## Fixtures`, `## Scenarios` as numbered sections, `## Grading`. Match its register — terse, binary, a short sentence after each table naming the failure that scenario exists to catch. Match its dash and heading style too; this is a sibling document, not a new house style.

Two rulings on where the precedent and the constitution meet, so you do not have to guess:

- The precedent labels each scenario's prompt and repo with standalone `**Prompt:**` and `**Repo:**` lines. That is not what C-13 bans. C-13 bans the *bulleted* inline header, `- **Thing:** description`, used to fake structure inside a list. Standalone label lines are fine and you should use them.
- The precedent states its fixtures once in a global `## Fixtures` block. You need that section too, but it does not satisfy C-2: every scenario must *also* name the fixture it runs against, inside its own section. A fixture named only in the global block leaves that scenario failing C-2.

**The method.** Each scenario runs the same prompt twice, once with the skill loaded and once without, and the delta is what gets graded. The no-skill baseline is the step that tells you whether the skill taught anything, so every scenario has to say what the baseline is expected to get wrong — specifically, naming a token it omits, a section it invents, or a tier it picks instead, not merely that it does worse. The test to apply to each baseline sentence: would it stay true pasted into a different scenario, with or without its fixture name swapped? If so it has said nothing, and swapping in the right fixture name does not rescue it.

**Running a scenario.** Include a run-procedure section. It routes through `_maintenance/inbox-to-memory/eval-scope.sh`, which stages a fixture into scratch and prints the path. Staging happens once per run, not once per scenario: process mode empties `_inbox/`, so the with-skill and without-skill runs each need their own copy. Neither any scenario nor any step of the procedure may name a `tests/fixtures/` path as the directory the skill is run against.

**The scenarios.** At minimum these four behaviors, each with its own scenario, each naming its fixture, its verbatim prompt, and a table of pass conditions:

1. **Contradiction round trip, end to end.** From the phase 2.5 flag against a `status: accepted` record, through phase 5 sign-off, into the amend outcome. Its pass conditions name the artifact each step produces: the inline `[contradicts accepted: [[...]]] <statement> | claims: <what the record says>` flag with both halves, the line rewritten to `[[<target>|memory — updated]]`, the source note's `id` appended to the target's `source_refs`, and the amended passage marked `(added YYYY-MM-DD, <note-id>)`. Detection alone is not the round trip.
2. **Unacknowledged tension**, with the negative case in the same table. The rule is at `SKILL.md:122`, and its two halves live in different files — the count over prior notes in `notes/`, the acknowledgement in the `_inbox/` transcript. The fixture is built that way; grade it that way.
3. **Scope proposal at all three tiers, plus the tiebreak.** Project, client, and journal each on their own input, plus a fourth carrying two tiers of signal where the narrower token is correct.
4. **Tier 2 summary and entities.** Every row decidable by reading that note's emitted extract: entities appear verbatim in it, and the summary asserts no date, name, decision, or outcome the extract lacks. At least one row covers a plausible-but-unsourced summary that must be rejected. Nothing in this scenario is graded on quality, usefulness, or readability — those are unscoreable, and this is the scenario most likely to drift into them.

You may add scenarios beyond these four where the fixtures support one.

**Grading.** The `## Grading` section ships the empty table a run fills in, and that table has somewhere to record the without-skill result beside the with-skill one. The delta is the measurement; a results table with no room for the baseline throws it away.

**Vocabulary fidelity, and the failure most likely to sink this.** Every inline token you cite must be a shape registered in the ten-row grammar table at `references/machine-contracts.md`. Every phase number, frontmatter key, `status` value, `memory_type`, folder name, lint failure code, and script path must appear in `SKILL.md` or its references with the same spelling and meaning. An eval that grades against a token the skill does not emit is worse than no eval, because it fails work that was correct. The specific trap: `[memory candidate: journal]` is not a token — journal candidates take no scope token.

Do not describe the fixtures from imagination. Open each one and write the scenario against what is actually planted in it.

Touch only `_maintenance/inbox-to-memory/EVALS.md`. Do not update the `_maintenance/` inventory in the repo root `README.md` — its staleness is a declared non-goal and editing it fails C-1. Do not commit.
