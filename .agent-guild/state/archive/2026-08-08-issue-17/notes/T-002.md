Built `tests/fixtures/inbox-to-memory/evals/contradiction-amend/`, six files, nothing outside it.

## What's planted

The engagement is Rowan, a POS replacement at Larkspur Supply, a farm-and-home chain. Cast is fresh rather than borrowed from `mixed`/`old-only`, so nothing bleeds between scopes.

- `_memory/rules/refund-approval-code-ypAes5QNas.md` — `status: accepted`, the target. Claims every refund over $500 takes a district manager approval code, and its Known Exceptions section says "None," so the claim is universal and checkable.
- `_inbox/2026-04-21-118-service-desk-walkthrough.md` — raw live-typed notes from a store visit. A $912 warranty claim goes back on a customer's card out of the service desk claims console with no code, and Ruben says desk claims have never taken one at any amount. That cannot both be true with the record.
- `_memory/context/receipt-barcode-lookup-Qj2vTy_2pZ.md` — `status: superseded`, decoy. The input shows a card lookup with no receipt, contradicting it head-on. No flag expected.
- `_memory/decisions/self-checkout-refunds-DPtlHN4Ut4.md` — `status: proposed`, decoy. The input says both pilot stores turned self-checkout refunds on. No flag expected.
- Two prior v1 notes under `notes/`, the sources the two live records were crystallized from, each carrying its promoted candidate line as a resolved wiki link.

Three records total, so phase 2.5's five-body-read budget can't be what decides detection.

## Taste calls

**Amend, not supersede, is nailed down in the input.** The task turns on the record being right but incomplete, and that's the easiest thing to get subtly wrong. Two lines carry it: Ruben's "Nothing changes at the register. That one's right," and his objection being "to writing the desk into a rule that was never about the desk in the first place." The $500 threshold survives untouched; what's missing is a second channel and its compensating control (vendor claim number, weekly claims report to the DM, chargeback against store shrink). Amending adds a Known Exception with that control. Superseding would throw away a rule nobody thinks is wrong.

**I closed the dismiss escape hatch on a revision.** The first draft made the $912 transaction an even unit-for-unit exchange, which let a grader argue an exchange isn't a refund and the two never actually disagreed — the "different subjects wearing the same word" case in `references/extraction-heuristics.md`. Rewrote it so the model is discontinued and $912 goes back on the card. Money moves, above the threshold, no code. There's no reading where that isn't a refund the rule claims to cover.

**The seam is foreshadowed in the prior notes but not given away.** The 2026-02-24 note's unstated assumption is that "refund" and "what the POS calls a refund" were used interchangeably all morning; the 2026-03-31 note's is that everyone counts refunds out of the POS report because it's the only count there is. Phase 2.5 never reads prior note bodies, so this costs the skill nothing — it's the evidence a human grader uses to confirm amend was the right call.

**Whole fixture is v1.** No `schema` key anywhere. The spec blesses v1 as legal forever, and the scenario grades process-mode judgment rather than schema conformance, so v2 would only have added a frontmatter failure surface. Frontmatter keys are still written in contract order and single-line inline arrays throughout, so the scope migrates cleanly if anyone ever wants it to.

**No README in the fixture directory.** The scenario prose belongs to the eval doc, and a second description of the same fixture is a thing to keep in sync and a thing to contradict.
