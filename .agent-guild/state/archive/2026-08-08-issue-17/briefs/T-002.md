## Spec excerpt

Build one fixture for the inbox-to-memory eval suite: the scope that exercises **contradiction detection against accepted memory**. You are building a fixture only. The doc that grades against it is a separate task; write no prose about it.

Own exactly one new directory under `tests/fixtures/inbox-to-memory/evals/`, named for what it holds. Sibling tasks are building other fixtures under that same path — do not touch theirs, and do not build anything but the contradiction scope here. Keeping one behavior per fixture is deliberate: the skill's detection reads whole transcripts, so unrelated content planted in the same scope can silently trip or suppress a neighbouring scenario.

A fixture is an opted-in scope the skill can run in process mode: a directory holding `_inbox/` plus `_memory/`. Read `inbox-to-memory/SKILL.md` phases 1 through 3, phase 2.5 especially, before planting anything. The existing scopes under `tests/fixtures/inbox-to-memory/` (`old-only`, `mixed`) show the file shapes; match their conventions, including nanoid-suffixed filenames.

**What to plant.** One `_memory/` record with `status: accepted` making a specific, checkable claim, and one `_inbox/` input that contradicts that claim head-on.

The contradiction has to be real. An input that merely mentions the record's subject produces no flag, and a fixture built that way grades correct behavior as a failure. Only `accepted` records produce flags at all — a `proposed` record hasn't been agreed to yet and a `superseded` one is already known wrong — so if you plant decoy records to make detection non-trivial, give them one of those statuses and expect no flag from them.

The scenario built on this fixture will follow the contradiction through phase 5 sign-off into the **amend** outcome, so the record needs to be one amending makes sense for: right but incomplete, rather than flatly wrong. A record that supersession fits better than amendment is the wrong plant.

Phase 2.5 normalizes entities through the scope's alias table before any lookup, and reads at most five record bodies per input. Keep the scope small enough that the budget is not the reason detection succeeds or fails.

**Constraints.**

- `bash inbox-to-memory/scripts/lint-scope.sh <your fixture>` must exit 0. Run it before you finish.
- Check your tokens by hand as well, because the lint will not do it for you. Its token-grammar pass runs only over files carrying `schema: 2`; on a v1 file it reads no tokens at all and exits 0 on a token that does not exist. So a misspelled `[open question: ...]` or an invented `[memory candidate: journal]` ships green and silently disables the behavior the scenario grades. Match every inline token you write against the ten-row grammar table at `references/machine-contracts.md` yourself. The rule is scoped to note bodies above `## Raw Content` — brackets in frontmatter and brackets inside raw content are legal and are not tokens.
- No `MEMORY.md`, `INDEX.md`, or `index.md` anywhere under a `_memory/` path. The smoke suite walks the whole fixtures tree for those and fails on any hit.
- v1 files (no `schema` key) are legal forever and the lint never flags them, so v1 is a fine choice. If you write v2 frontmatter it has to be correct, in the key order at `SKILL.md`'s frontmatter quick reference.
- Content should read like real consulting notes. The skill's extraction heuristics need something to bite on, and a fixture of filler makes the eval it feeds unconvincing.

Touch nothing outside your one new directory. In particular, do not update `tests/fixtures/inbox-to-memory/README.md` — its staleness is a declared non-goal, and editing it fails C-1. Do not commit.
