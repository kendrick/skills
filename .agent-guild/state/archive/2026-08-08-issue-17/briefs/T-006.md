## Spec excerpt

Build one fixture for the inbox-to-memory eval suite: the scope that exercises **scope-tier proposal**, at all three tiers plus the tiebreak. You are building a fixture only. The doc that grades against it is a separate task; write no prose about it.

Own exactly one new directory tree under `tests/fixtures/inbox-to-memory/evals/`, named for what it holds. Sibling tasks are building other fixtures under that same path — do not touch theirs.

Read `inbox-to-memory/references/scope-decisions.md` in full before planting anything, and `SKILL.md` phases 1 and 3. This is the fixture where the layout matters: a project sits at `pursuits/<name>/` or `projects/<name>/` inside a client root that is itself opted in, and a client root is the directory containing those. Build a client root with at least two project directories under it.

**What to plant.** Four `_inbox/` inputs, each one that `references/scope-decisions.md` routes to a specific tier:

1. one the reference routes to **project** — a fact bound to a single project's deliverable, contract, or technical decision
2. one it routes to **client** — a stakeholder relationship, environmental fact, or operating rhythm holding across the client's projects
3. one it routes to **journal** — a pattern that generalizes beyond this client, or content in the reference's generalizing register
4. one carrying signals at **two tiers at once**, which Conflict Resolution at `scope-decisions.md:21-25` resolves to the narrower token

That fourth input is the one the whole scenario turns on. "Project is the floor" is the rule being tested, so it has to be a genuine conflict — an input a careless reader would route to client, that the tiebreak keeps at project.

**Read each input back against the signal table before calling it done.** An input mentioning a stakeholder's reporting line is a client-tier signal whatever you intended it to be, and an input that "generalizes" in tone without actually generalizing beyond this client is not a journal signal. The reference also says what never goes to journal: single-instance observations, anything bound to a specific person or deal, anything that would not make sense read 18 months later. A journal input that trips one of those is built wrong.

**If you use the recurrence signal** — "subject entity has already been referenced in 2+ projects' notes at this client" — the fixture has to actually hold those references, in distinct project directories, with the subject named in the notes there. It is the one signal in the table that is not readable off the input alone, and the one place a well-formed fixture can still grade nothing.

Where the four inputs live is your call, as long as each is somewhere the skill's phase 1 walk resolves to a scope that makes sense for it. Note that journal candidates take no scope token and route to the cross-client journal regardless of which scope the input was groomed in.

**Constraints.**

- `bash inbox-to-memory/scripts/lint-scope.sh <scope>` must exit 0 for the client root and for each opted-in project subdirectory. Run it on each before you finish.
- Check your tokens by hand as well, because the lint will not do it for you. Its token-grammar pass runs only over files carrying `schema: 2`; on a v1 file it reads no tokens at all and exits 0 on a token that does not exist. `[memory candidate: journal]` — the trap named below — passes the lint clean on a v1 file. Match every token against the ten-row grammar table at `references/machine-contracts.md` yourself. The rule is scoped to note bodies above `## Raw Content`; brackets in frontmatter, brackets inside raw content, and the illustrative `[memory candidate]` / `[topic]` examples the `CLAUDE.md` templates carry are all legal and none is a token.
- No `MEMORY.md`, `INDEX.md`, or `index.md` anywhere under a `_memory/` path. The smoke suite walks the whole fixtures tree for those.
- Every inline token must be a shape registered in the grammar table at `references/machine-contracts.md`. `[memory candidate: journal]` is not a token and never was — journal candidates carry no scope token.
- A client root wants a `CLAUDE.md` declaring its memory mode, since the mode decides which `memory_type` vocabulary applies. Follow the shape in `inbox-to-memory/assets/claude-md/`.
- Content should read like real consulting notes across two engagements at one client. The tier signals have to arise from the content, not from labels stuck on it.

Touch nothing outside your one new directory tree. Do not update `tests/fixtures/inbox-to-memory/README.md` — its staleness is a declared non-goal and editing it fails C-1. Do not commit.
