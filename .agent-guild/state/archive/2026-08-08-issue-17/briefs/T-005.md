## Spec excerpt

Build one fixture for the inbox-to-memory eval suite: the scope that exercises **unacknowledged-tension detection**, both branches of it. You are building a fixture only. The doc that grades against it is a separate task; write no prose about it.

Own exactly one new directory under `tests/fixtures/inbox-to-memory/evals/`, named for what it holds. Sibling tasks are building other fixtures under that same path — do not touch theirs, and plant nothing in yours but what this behavior needs.

A fixture is an opted-in scope the skill can run in process mode: `_inbox/` plus `_memory/`. Read `inbox-to-memory/SKILL.md` phase 3, and its "Open Question Slugs" subsection in particular, before planting anything. The scopes under `tests/fixtures/inbox-to-memory/` show the file shapes; match their conventions, including nanoid-suffixed filenames.

**The rule, at `SKILL.md:122`.** Flag a slug open across three or more notes as `[tension: unacknowledged]`, unless the transcript shows someone naming it out loud.

The two halves of that rule live in different files, and getting this wrong is the single likeliest way to build a fixture that grades correct behavior as a failure:

- The **count** is over prior notes under `<scope-root>/notes/`. That is where the skill's recurrence grep reads.
- The **acknowledgement** is in the `_inbox/` transcript being groomed. Process mode never edits or re-reads a prior note for it, so an acknowledgement planted in a prior note is planted where the rule does not look.

**What to plant.** Two open-question slugs, each carried across three or more prior notes under `notes/`:

- a **positive** slug, where no `_inbox/` transcript in the fixture names its question aloud, so the skill should flag it
- a **negative** slug, where an `_inbox/` transcript does name its question aloud, so the skill should not flag it

The negative case has to turn on the acknowledgement. If it goes unflagged because only two notes carry it, the fixture tests nothing it claims to and the eval built on it is worthless.

**The interference trap.** The rule reads the transcript, not a designated passage in it. A transcript that names the positive slug's question in passing — a stray "we still haven't pinned down who owns the freeze date" — suppresses the flag the positive case exists to produce, and every other check here still passes. Read every `_inbox/` file back against both slugs before you finish, and confirm the positive question is genuinely unspoken in all of them.

Reuse the same slug text that already appears in the notes rather than minting a variant. The skill greps for slugs already in play precisely so a question does not fragment across spellings.

**Constraints.**

- `bash inbox-to-memory/scripts/lint-scope.sh <your fixture>` must exit 0. Run it before you finish.
- Check your tokens by hand as well, because the lint will not do it for you. Its token-grammar pass runs only over files carrying `schema: 2`; on a v1 file it reads no tokens at all and exits 0 on a token that does not exist. This is the failure mode that would quietly ruin *this* fixture in particular: write `[open-question: freeze-owner]` instead of `[open question: freeze-owner]` and the lint stays green, the recurrence grep never matches, the count never reaches three, and the scenario built on it grades nothing. Match every token against the ten-row grammar table at `references/machine-contracts.md` yourself, and check that the slug is spelled identically in every note carrying it. The rule is scoped to note bodies above `## Raw Content` — brackets in frontmatter and brackets inside raw content are legal and are not tokens, so the slug has to appear above the fence to count.
- No `MEMORY.md`, `INDEX.md`, or `index.md` anywhere under a `_memory/` path. The smoke suite walks the whole fixtures tree for those.
- v1 files (no `schema` key) are legal forever and the lint never flags them. If you write v2 frontmatter it has to be correct, including the `open_questions` derived count.
- The notes should read like a real engagement where a question kept not getting answered across weeks. That arc is the thing being detected, and a fixture that just repeats a token three times does not produce it.
