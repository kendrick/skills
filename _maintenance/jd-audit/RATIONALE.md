# jd-audit Skill Rationale

## Why This Exists

A validator that also decides how to fix what it finds is making two different kinds of claim in one script: what's true, and what should happen about it. jd-audit keeps those separate on purpose. `scripts/validate.py` only answers the first question—every check below exists because some specific piece of drift needed a name and a severity, not because a script should also get to pick sides when the register and the folders disagree.

## Where the Evidence Comes From

The check catalog and its contract—CLI flags, exit codes, finding shape—are frozen in the validator spec this skill was built against. The day-one drift each check has to catch (`11.03 Cobalt Freight` vs. `11.03 Cobalt`, the three-way client collision at `15.01`/`15.02`, the `13`-category label mismatch against the constitution, the Protogen split at `13.02`/`14.02`, and the one real fourth-tier folder at `80.01.01`/`80.01.02`) comes from a scan of the actual vault, not a hypothetical. Prior art credited for structural ideas is in [`_maintenance/jd/SOURCES.md`](../jd/SOURCES.md); the full analysis is [`_docs/jd-ngerakines-plugin-report.md`](../../_docs/jd-ngerakines-plugin-report.md). Rows below marked `scan` trace to the vault scan; rows marked `local` are this user's own call.

## Decision Ledger

| Decision | Source | Reason |
| --- | --- | --- |
| `drift-split-name` uses exact-normalized matching only—case folded, whitespace collapsed—with fuzzy matching considered and deferred | local | A fuzzy matcher would catch more real splits, but it would also catch more coincidences, and a false positive here costs more than a missed one: the first time the validator cries wolf on two unrelated IDs that happen to sound alike, the fix is to stop reading its output, which loses every check it runs, not just this one. |
| `structure-deep-numbering` fires only on a fourth *numbered* tier; unnumbered nesting below an ID stays silent | scan; corrects `ngerakines/jd` | The prior art states flatly that all files live in ID folders and treats anything nested deeper as a fault. This vault's client scopes run ten directories deep on purpose—`_memory/`, `projects/`, their own git repos—and none of it is numbered. Adopting the prior art's rule as written would flag the user's entire working substrate as broken. The invariant that actually holds is narrower and still catches the real defect: numbering stops at `AC.ID`, so a name matching `[grammar].deeper` (`80.01.01`) is a fourth numbered tier and gets reported, while everything else below an ID stays silent because it was never supposed to be numbered in the first place. |
| `00.02 Vault Conventions.md` lives in the vault, not in this skills repo | local | The validator and both skills' prose need to parse one definition of this vault's dialect, and a copy checked into the skills repo would drift from the vault the moment either side changed without the other. Keeping it in the vault also means it syncs to every machine the vault syncs to, and a consumer that isn't this repo at all—a human editing it by hand, some future script—can read it without touching a git checkout. |
| Severity split: register/substrate drift is `error`, `drift-split-name` is `warn`, `link-unverifiable` is `info` | local | The three tiers track how much judgment a finding still needs before it's actionable. A register entry and a substrate disagreeing about whether an ID exists is unambiguous—one of the two is simply wrong, so it's an error. A name recurring under two IDs might be a real split or a name that's legitimately repeated (an "Archive" folder in more than one area), so it's a warning asking for a human call rather than a declared fault. An absolute `file://` link this host can't verify might just belong to a different machine's mount point, which is normal, so it's informational only. |
| Two skills, not three—full decision in `jd-file` RATIONALE |—| Cross-reference. The short version: entry repair, fixing a register line once drift is found, belongs to reconciliation, which is this skill's job, not a third skill's. |
| Portability debt is tracked in `jd-file` RATIONALE, not duplicated here |—| Cross-reference. The seam test and the public-release path apply to the validator the same way they apply to filing—a second Johnny.Decimal system should need only a new conventions note and register, never a change to `scripts/validate.py` itself—so the ledger lives in [one place](../jd-file/RATIONALE.md#portability-debt) rather than two that could drift from each other. |
| The one-time Overview stamper reports anything it does not recognize | local | Stamping the wrong file is the worse error. A digest on an Overview someone wrote into freezes their writing as furniture and makes an occupied ID report empty—the same silent failure `hygiene-empty` exists to prevent, arriving from the other direction. So the heuristic is deliberately narrow: an Overview qualifies only when its `## Context` is empty, its `**Next action:**` is unfilled, its `## Log` holds only lines `jd-file` writes, and it carries no section the template never put there. That last condition goes beyond the three the issue named, in the safe direction—a person's own `## Ideas` heading is writing, whatever the sections around it look like. A false skip costs one decision; a false stamp costs an ID nobody can see is occupied. |
| Byte-identical script vendoring, not importing across skills—full decision in `jd-file` RATIONALE |—| Cross-reference. The short version: a shared script only works as one contract if it can't quietly drift, so `resolve_vault.py` and `scaffold_digest.py` are vendored byte-identically into every skill that needs them rather than imported, with a `cmp` check in each smoke test to catch drift. This skill carries a copy of both under that rule. |
