# mutation-testing—rationale

Evidence tiers: **[E]** measured or observed in a real run, **[P]** practitioner reasoning from prior art, **[C]** convention inherited from this repo or its neighbors.

## Where This Came From

One observation and two rounds of evidence on top of it.

- **kendrick/skills#108**, the issue. Two `code-review` passes across four subagents returned nothing that changed a line on a ticket whose entire content was a new rejection rule. An unprompted mutation run on the same code produced four measurements in minutes, including the one that became the most useful sentence in the pull request: hoisting a read out of its write transaction fails exactly one test and leaves 62 green. Reading a diff cannot produce that, and nothing in the toolkit asked for it.
- **The three rules in that issue**, each learned by getting it wrong in that run: mutate the plausible refactor rather than an arbitrary break (21 meaningless failures versus 1 that mattered), restore by file rather than by directory (`git checkout -- app/storage/` reverted the new test alongside the mutation and the suite came back green without it), and re-measure after the suite grows (one mutation moved from 2 failures to 4 once a later test began exercising the same return value).
- **The issue's own comment**, offering two later measurements as evidence rather than as an edit to the criteria. Both were folded in: the plausible-refactor rule turns out to have a scope, and mutations running one at a time is a boundary worth writing down.
- **kendrick/cambium#84 and kendrick/cambium#95**, whose whole content is a guard on a `package.json` script, mutation-tested three times across two rounds by hand because no skill asked for it. The mutation that found the defect was an arbitrary break the plausible-refactor rule says not to try: `oxfmt --write . >/dev/null && oxfmt --write` rewrites the whole tree with the summary discarded, then formats the one file it was handed and reports `on 1 files`. The guard had been reading the file count oxfmt prints about itself, so it passed while the tree-wide write it exists to catch had already happened. A second round repeated the shape with a write scoped to a nested path.
- **kendrick/cambium#87 and cambium's `docs/agents/testing.md`**, which already require the check—mutate the branch, confirm a test fails—and are where the verdict question was already live before this skill existed.

## Decision Ledger

| # | Decision | Why | Tier |
|---|---|---|---|
| 1 | Model-invoked, with a trigger-bearing description and no `disable-model-invocation` | The issue's premise is that nothing in the toolkit asks for this measurement, so a missed trigger costs a guard its only check, while a misfire costs one mutation run and a restore. That is the inverse of the asymmetry behind `adversarial-review` and `work-issue`, where a misfire spends a whole fan-out. The body says so in one line, the way the user-invoked siblings justify themselves. | [P] |
| 2 | Two mutations per guard, one per question, rather than one rule carrying a caveat | The output shapes differ and neither mutation can answer the other's question: a plausible mutation measures how much of the suite notices a refactor, and an adversarial one returns a verdict on whether the guard watches the right quantity. Measured across three by-hand rounds on kendrick/cambium#84 and #95, where the plausible half stayed silent through both rounds that found the defect. Folded into one skill rather than split into two, per the user's call on the issue comment. | [E] |
| 3 | The refactor question takes the plausible mutation, never an arbitrary break | Measured in the run behind #108: mutating a read into a form that stalls under the test double produced 21 failures and meant only that the test double was load-bearing. Hoisting the read above its transaction—the version a reviewer would approve without comment—fails 1 test, and that one test is the answer. | [E] |
| 4 | Restore by name, one path at a time, with `git status --porcelain` diffed against a pre-mutation snapshot | `git checkout -- app/storage/` reverted the new test alongside the mutation, and the suite came back green without it. That was caught on the test count rather than by noticing, so the honest description is a near miss. The snapshot comparison is what turns a near miss into a hard stop, because the failure is invisible in a passing suite and nothing else in the loop looks at it. | [E] |
| 5 | Every mutation re-runs against the final suite before any count leaves the run | One mutation moved from 2 failures to 4 once a later test began exercising the same return value. Extrapolating from the earlier run puts a wrong number in a pull request, where it is read as a measurement. The bound is any edit to a test file, not any edit at all, and the trigger is a number leaving the run rather than the run ending. | [E] |
| 6 | Counts are quoted from the runner's own summary line, verbatim, and nothing parses it | Runners disagree about what they report and about how they phrase it, so a parser would be wrong per project and silently. The line as printed is what a reader can check against their own run. This is the consumer's-units rule applied to a test runner: assert what the runner said, not a count reassembled from it. | [P] |
| 7 | A red baseline stops the run | A failure that was already there is indistinguishable from one a mutation caused, so every count downstream inherits the ambiguity while still reading as a measurement. | [P] |
| 8 | No script. Choosing a mutation, reading a verdict, and ruling on an equivalent mutant all stay in the prose | Choosing the plausible refactor is judgment, the suite is the project's own command, restore is a copy-back, and the restore check is one `git status` comparison. None of it wants a diff tool, and this repo's rule is that where judgment is the job it stays in the prose. | [C] |
| 9 | The name keeps "mutation" despite this repo's other sense of the word | `work-issue`'s "Prove the mutation, then read the result" means an edit that may have silently failed to apply. The issue title asks for `mutation-testing`, the term is the industry's, and both senses want the same discipline, so the preamble draws the line in one sentence rather than the skill taking a worse name to avoid it. | [C] |
| 10 | A `slipped` adversarial verdict is reported first, ahead of every measurement | It is a defect in the guard rather than a measurement of the suite, and the two read differently: a measurement invites a judgment call about coverage, while a slipped verdict says the guard is watching the wrong quantity and the numbers beside it describe nothing. | [P] |
| 11 | The applied mutation is proved on disk before the suite runs | An edit that silently failed to apply leaves the suite green, and a green suite reads in this skill as "no test catches this"—the exact inverse of what happened, arriving as a confident measurement. `work-issue` carries the same rule for the same reason, after losing five edits that way in one session. Not in the issue or the plan; added while writing Step 3, because this skill's output is precisely the reading a silent failure corrupts. | [P] |

## Deliberately Not Built

Each row below is pinned by a `refute_text` assertion in `tests/mutation-testing-smoke.sh`, because every one of them is a reasonable-sounding idea and a well-meaning edit is exactly how it comes back.

| Cut | Why |
|---|---|
| Parallel mutations, or a worktree fan-out for speed | Restore is already the fragile step at concurrency one. Two mutations sharing a tree restore against the same snapshot and race over the same paths, which turns a fragile step into a correctness bug that reports a clean run. The only safe shape is a worktree per mutation, and the boundary is written down so the cheap version does not get built by accident. |
| A mutation-operator engine in the `mutmut` or Stryker shape | Those generate arbitrary breaks exhaustively, which is the one thing decision 3 measured as worthless here: 21 failures that meant nothing. The mutations worth running are the plausible refactor and the adversarial route, and both are readings of the code rather than enumerations of it. |
| A persisted run directory | The report is the artifact and it goes in the reply. A run directory would hold counts that decision 5 already says go stale the moment a test file changes, which is a stored measurement with a shelf life nobody can see. |
| Parsing the runner's output into structured numbers | Decision 6. A parser is wrong per project and silently, and the summary line is quoted precisely so a reader can check it. |
| Mutating anything the diff did not add | The trigger is what the diff adds, and a run that wanders into surrounding code produces findings about work nobody is reviewing, on a budget the guard's own check was meant to spend. |
| Restoring with a directory-form `git checkout -- .` or a path prefix | Decision 4. This is the exact command that reverted the new test alongside the mutation. |

## Known Limitations

- **A guard with no test yields a row, not a mutation.** There is nothing to measure, so the absence is reported and the run moves on. Whether the guard should have a test is a judgment for the reader.
- **Suite runtime bounds how many mutations a run can afford.** Two mutations per guard against a suite that takes ten minutes is twenty minutes per guard, serially, and Step 4 re-runs all of them. On a slow suite the honest move is fewer guards per run rather than fewer mutations per guard.
- **The snapshot sees tracked and untracked paths, never ignored ones.** `git status --porcelain` says nothing about a file in `.gitignore`, so a mutation that writes into an ignored build directory restores unverified.
- **An equivalent mutant reads as `slipped`.** A mutation no test could distinguish, because it does not change observable behavior, produces the same verdict as a real gap in the guard. Telling the two apart is a human's ruling, and the report says which rows are waiting on one.
