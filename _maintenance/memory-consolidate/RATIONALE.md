# memory-consolidate—rationale

Evidence tiers: **[E]** measured or observed in a real run, **[P]** practitioner reasoning from prior art, **[C]** convention inherited from this repo or its neighbors.

## Where This Came From

Four sources:

- **Issue #195**, which asked for a report-only health pass over a scope's `_memory/` and set the acceptance criteria the smoke suite pins. Near-duplicate detection was in its first draft and left it on 2026-11-02 for kendrick/long-term-memory-kit#130.
- **#276, merged as #279**, which made a scope's `_memory/` a valid long-term-memory-kit Bank. Before it, `ltm doctor` couldn't read a scope.
- **The kit's `docs/doctor.md`**, which fixes the shape this skill consumes: `ltm doctor --bank <path> --json` prints an array of `{file, check, message, related_files}` objects, exits 0 whenever the checks ran, and exits 1 outside a Bank, on a bad `doctor:` block, or on an invalid `LTM_TODAY`. Its `stale-confirmed` dismissal paragraph is the source of the `ltm confirm`/`ltm deprecate` pointer in `SKILL.md`.
- **`inbox-to-memory`'s Phase 5** and the token grammar in `inbox-to-memory/references/machine-contracts.md`. The amend form `[memory candidate: update existing [[<file>|<label>]]] <claim>` is already registered there with its grep, and Phase 5 already resolves it.

## Decision Ledger

| # | Decision | Why | Tier |
|---|---|---|---|
| 1 | One stdlib script, `scripts/consolidate.py`, taking `--scope <root>` and an optional `--json <file>` | Turning a doctor array into lines is the same job every run, so a script does it the same way each time. Standard library only keeps the skill copy-in portable, per `AGENTS.md`. `--json` reads doctor output saved earlier, which lets the suite run without the kit and lets a user hand over a file made on another machine. `SKILL.md` keeps the judgment: when to run, how to present the report, and where the user goes next. | [C] |
| 2 | The report is a groomed note in drain form: frontmatter `schema: 2`, `id`, `date`, `type: report`, `open_questions: 0`, `resolved_questions: 0`, `deferred_tensions: 0`, and `unpromoted_candidates`, in `machine-contracts.md`'s note key order, then one `[memory candidate: update existing [[<stem>\|<title>]]] <check>: <message>` line per finding, with a `related: [[<stem>]], ...` tail where doctor named related files | Every grep, the `unpromoted_candidates` count, and Phase 5 already read this token, so nothing downstream needs teaching. `machine-contracts.md` has a v2 note carry all four counts even at zero, and Phase 5's update-existing path appends the note's `id` to the record's `source_refs`, so the report carries both. A new report format would need its own row in `machine-contracts.md` and its own handling in Phase 5. The title comes from the record's frontmatter `title`, else its stem, so the line shows the name the record gives itself. | [P] |
| 3 | Routing never names a check | `consolidate.py` turns every finding into a line the same way, whatever its `check`. A check the kit adds later, such as `near-duplicate` from long-term-memory-kit#130, comes through with no change here. The suite proves it with a stubbed `unseen-check` finding, which the report carries as a candidate line. | [P] |
| 4 | Resolution belongs to Phase 5, and this skill never writes a record | Phase 5 already has the per-candidate review and the update-existing path: approving a line amends the record, appends the report's `id` to its `source_refs`, and rewrites the line to `[[<target>\|memory — updated]]`. A line the user declines keeps its candidate prefix and takes Phase 5's `\| dismissed:` suffix, which drops it from `unpromoted_candidates`. A second resolver here would duplicate that path and could drift from it. For `stale-confirmed`, the usual fix is `ltm confirm` or `ltm deprecate`, which the user runs. `consolidate.py` writes only the report path. The suite checks that `git status --porcelain _memory/` is empty after a run and that the report is the only new file. | [P] |
| 5 | Same scope, same `LTM_TODAY`, same bytes | The report holds no time of day, no random id, and no absolute path, and the date comes from `LTM_TODAY` where set. Doctor's thresholds count days from today, so the fixture's saved `doctor.json` reproduces byte for byte only with `LTM_TODAY=2026-10-01`. Unpinned, more fixture records age past a threshold. The suite's case 10 runs the real `ltm` on the fixture bank at that date and checks its report against the same expected bytes the saved `tests/fixtures/memory-consolidate/doctor.json` gives. The suite also runs the pass twice and compares the bytes with `cmp`. | [E] |
| 6 | Model-invocable, with a trigger-bearing description | A misfire writes one report file under `notes/reports/` and touches no record, so it costs little. The description names the triggers ("consolidate memory", "check memory health", "find stale records") and says the skill never writes records, naming `inbox-to-memory` for that. | [P] |
| 7 | Thresholds come from the scope's `memory-bank.yaml` `doctor:` block, and the skill passes none of its own | Doctor reads them there. A second set of thresholds in this skill would let the report and a direct `ltm doctor` run disagree about the same Bank. | [P] |
| 8 | Exit codes: 0 report written, 1 `ltm doctor` failed or couldn't run or its JSON isn't an array of `{file, check}` objects, or the script refused to overwrite a same-day report (row 9), 2 argparse usage error, 3 unreadable scope, unreadable `--json` file, or an `LTM_TODAY` not exactly `YYYY-MM-DD` | Borrows the codes of the validator convention `check-territories.py` set. `AGENTS.md` requires that convention only of scripts that gate a run, and this one writes an artifact, but one set of codes across the repo's scripts is easier to read. A usage error exits 2 because argparse exits before the script's own code runs, as in `memory-index`. `ltm` missing from PATH exits 1, with doctor's other failures, since the input was fine and doctor couldn't run. When doctor fails, stderr quotes its output and no report is written. The refusal takes 1 as well, since #288 asked for it and the input was readable. `SKILL.md` tells it apart from doctor's failures by its `consolidate: refusing to overwrite` prefix, which the suite pins in the script and in `SKILL.md`. | [C] |
| 9 | The script refuses a same-day rerun over a report holding a line Phase 5 resolved, and `--force` overrides it | Same day means same path. Phase 5 rewrites each line it resolves, so a silent rerun would throw away decisions already made. Approval rewrites a line's prefix to `[[<target>\|memory — updated]]`, so an approved line starts with `[[`. A dismissed line keeps its prefix and gains `\| dismissed:` (row 12). Those two marks are the only parts of Phase 5's grammar the script learns. An open candidate also holds `[[`, but mid-line, so a substring test would refuse every rerun. The check runs before doctor, so a refused run makes no `ltm` call. A report the script can't read or decode is refused too, because the script can't prove it safe to replace. A check in `SKILL.md` alone would miss a user who runs the script directly. Step 1 shows the user the resolved lines and reruns with `--force` only on a yes. The suite's case 11 checks the refusal, the unchanged bytes, the empty `ltm` log, and the forced rewrite, and case 12 checks the same refusal over a dismissed amend. | [P] |
| 10 | The suite stubs `ltm` with a PATH shim, and also runs the real `ltm` when one is on PATH | The shim makes every case run without the kit and lets the suite feed doctor a failure, malformed JSON, or an unseen check. The real run compares its report against the same hand-written expected bytes, so a `doctor.json` that drifts from what the kit prints fails the suite. | [P] |
| 11 | The report's `id` is the first 10 bytes of a SHA-256 of `memory-consolidate:<date>`, each byte mod 64 indexing the nanoid alphabet `A-Za-z0-9_-` | `inbox-to-memory` takes every note id from `nanoid -s 10`. A random id would break row 5, since a same-day rerun would write different bytes. The hash keeps the id's length and alphabet, so the lint's id pattern and Phase 5's `source_refs` append treat it like any other note id. Inside one scope, two reports share an id only when they share a date, and then they share a path too. | [P] |
| 12 | The same-day refusal counts a line as resolved when it starts with `[[`, or when it starts with `[memory candidate: update existing` and holds `\| dismissed:` | Phase 5 dismisses a declined finding by appending `\| dismissed: <reason, and who decided>` and keeping the prefix (#289). The `[[` test alone read that line as open, so a rerun replaced the report and threw the dismissal away. An open line whose doctor message happens to hold `\| dismissed:` gets refused too. That costs the user a `--force` rerun, and no decision is lost. With the test cut back to `startswith("[[")`, the suite's case 12, a rerun over a report whose only settled line is a dismissed amend, exited 0 where it should exit 1. | [E] |

## Deliberately Not Built

| Cut | Why |
|---|---|
| A list of known `ltm doctor` checks | Any list goes stale the day the kit adds a check, and a filter keyed on it would drop that check's findings without saying so (row 3). Pinned by a `refute_text` on `stale-confirmed`, `long-chain`, and `orphan` in `scripts/consolidate.py`. |
| A similarity search of its own | Near-duplicate detection moved to long-term-memory-kit#130 on 2026-11-02. When it lands as a doctor check, row 3 carries its findings in. Pinned by a `refute_text` on `near-duplicate` and `similarity` in `scripts/consolidate.py`, and on `near-duplicate` in `SKILL.md`. |
| Writing records | Resolution is Phase 5's (row 4), and the kit's `ltm confirm` and `ltm deprecate` stay commands the user runs. Pinned by a `refute_text` on `confirm` and `deprecate` in `scripts/consolidate.py`, and by the suite's `git status --porcelain _memory/` case. |

## Known Limitations

- The path carries only the date, so the script can't keep two runs from one day. It refuses to overwrite a report holding a resolved line (rows 9 and 12), but it overwrites one with no resolved line, and `--force` overwrites either.
- A record title holding `|` or `]]` isn't escaped. It breaks the wikilink in that finding's line, and Phase 5 may misread the target.
- Two scopes' reports from the same day carry the same `id`, since the hash reads only the date. A record's `source_refs` resolve inside its own scope, so this matters only to a reader comparing ids across scopes.
- `consolidate.py` reads a title only from a single-line `title:` key. A title written as a YAML block scalar comes through as its first line, such as `>-`.
- `--json` doesn't check that the file came from this scope. Doctor output saved from another Bank still writes a report, and any record the scope doesn't hold gets its stem as its title.
