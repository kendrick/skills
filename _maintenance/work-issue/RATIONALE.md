# work-issue—rationale

Evidence tiers: **[E]** measured or observed in a real run, **[P]** practitioner reasoning from prior art, **[C]** convention inherited from this repo or its neighbors.

## Where This Came From

Five sources:

- **Issue #101 and the session behind it.** The loop this skill writes down was run five times in one session against `kendrick/cambium`—issues #54, #38, #42 and #17, plus four external-review repair rounds. It caught two errors in the orchestrator's own plans (an invented incompatibility between structured outputs and thinking, a false claim that a provider would make a bundle-budget test meaningful), both built to spec *and* flagged, because the dispatch said the plan might be wrong. It also produced the two failure modes rows 7 and 18 exist to close. Everything the skill knows that a reader would not guess traces to that session; the issue is where the numbers live.
- **This repo's `divvy-up`.** Wave derivation, the shape line as the user's correction point, the report contract, the wave gate, the one-rung-up retry, the failed-twice stop, and the workers-never-run-git rule. It stops at its Step 7 with a green verify and an assembled diff, which is exactly where this skill starts.
- **This repo's `adversarial-review`.** The rule a finding is a hypothesis until something that did not author it reproduces it, quoted rather than restated, and the trigger table Step 4's trigger matches the diff against, through the `match-triggers.py` script that ships beside it. Its roster is heavier than most diffs earn, so it became the last line of defense rather than the default (row 9).
- **This repo's `file-issue`.** The `gh auth status` preflight that degrades to a rendered draft instead of erroring, the rule that a rendered draft must never read as a filed issue, and the depth-governor idea that an input earns its own amount of process—which is what the Step 4 trigger does for the red-team phase.
- **This repo's `handoff`.** State that would otherwise live in a conversation is written to an artifact, a later session rebuilds from that artifact rather than from recollection, and it stops before acting. RUN_DIR is that artifact for a run, and the resume rule extends the precedent one step: git, `gh`, and herdr outrank RUN_DIR, because a run's own notes are what the crash that stranded it leaves stale.

## Decision Ledger

| 1 | Model-invocable (no `disable-model-invocation`) | A skill running a wave of issues reaches one lane through this one, and a user-invoked skill strips its description from siblings as well as from the agent, so no other skill can call one. That condition outranks the misfire asymmetry this row first weighed. Model-invocation adds agent reach without taking the human's away, so `/work-issue` still works, and Step 0's confirmation is what stops a misfire before anything is dispatched—with the push-and-pull-request half of its grant answerable separately from the build half. | [P] |
| 2 | An approved plan is required, and a thin one is refused rather than planned around | Every good outcome in the source session traced to a decision made before dispatch, and dispatching a thin plan buys a confidently-built wrong thing faster. | 3 | One confirmation up front, then unattended: fan-out shape and push authorization settled together | Confirming at first push instead parks every walk-away run at the gate, which is the property the whole design exists for. | 4 | Fan-out is proposed from the plan and confirmed, never chosen by a threshold | In the source session one of four issues was better as a single agent. A task-count threshold would have got that wrong silently; `divvy-up`'s shape line put it in front of the user as one sentence. | [P] |

| A Step 0 check or a stop for a missing `ponytail-review` | Row 165, and #252's Absence section. The skill is optional, and a run without it has to behave exactly as it did before, so Step 3 prints the skip line and carries on. A Step 0 check would refuse a run the plugin was never needed for, and a row in Where a Run Stops would end one. Pinned by a `refute_text` on `ponytail` in Step 0's section and in the Where a Run Stops section of `SKILL.md`, each cut out the same way. |
| An `--adopt-pr` flag | #143's decision, and row 166. The number's own type says which path it takes. Pinned by `refute_text` on `--adopt-pr` in `work-issue/SKILL.md` and `work-issue/README.md`. |
| Refusing a pull request that closes no issue | Row 170. The pull request body is the spec, and the in-scope test runs on the diff clause. Pinned by `refute_text` on `references no issue and no CRITERIA can be read` in `work-issue/SKILL.md`. |
| Telling a pull request from an issue by whether `gh pr view` fails | Row 166. A network failure reads the same as an issue number and sends a pull request down the issue path in silence. Pinned by `refute_text` on `gh pr view <n>` in `work-issue/SKILL.md`. |

## Known Limitations

- **A repository name ending in `.`, `_`, or `~` loses that character in route 4's URL reading.** Row 160 lets those characters close a URL so a sentence period or Markdown emphasis doesn't become part of the name, and the name match is lazy, so `github.com/o/repo_` reads as `o/repo`. A plan for `o/repo_` naming its own URL is then dropped as another repository's, and a plan naming `kendrick/skills_` survives for `kendrick/skills`. Names like that are rare, and passing the plan path on the argument line still works.
- **The newest triage round has two definitions.** `probe` picks it by highest round number k for `triage_newer_than_since`, `triage_inscope_rows`, `newest_repair_report`, `repair_ar_settled`, and `repair_diff_triggers`, and by file time, ties to the higher k, for `triage_blocking_rows` and `triage_stop_rows`, as their Probes rows said when #146 moved the gather into the script (row 129). Once Step 8 answers a row in an earlier round, those two can count a different round than the other five read. Each field is one gatherer now, so moving the two onto round number is a change to two functions.
- **A waived review's escalations stay in its own run directory.** When the Step 0 yes answers `adversarial-review`'s question, the review escalates what it reproduced and files nothing, and Step 5 does not carry those findings, or its UNVERIFIABLE ones, into the pull-request body. The human who merges sees them only in `.adversarial-review/runs/<run>/escalation.md`. PR #134 built that carry and cut it after three review rounds each found a hole in it: a resume after `ar-state.txt`, UNVERIFIABLE outcomes `ar-state.txt` does not count, a stale copy from an earlier attempt, and repos with a pull-request template. #138 takes it on with those findings as its spec.
- **The cross-run race is open.** Two invocations that both pass `check-inflight.py` before either writes its RUN_DIR both proceed, and the overlap surfaces as a rebase conflict at Step 5. Row 29 explains why it is recorded rather than locked. The window is the gap between the check and the first write in one invocation, and nothing in the skill narrows it further.
- **The reproducer only checks what the worker claimed.** `claims` is self-reported, so a change the worker never claimed is a change nothing reproduces. The Step 3 `code-review` against the issue and the Step 7 gate read the diff rather than the report, which is what covers the gap, and neither is a proof. Same shape as `divvy-up`'s self-report limitation, one level up.
- **The trigger's reading is judgment.** Row 112 has the session model decide, line by line, whether a matched signal implements a hazard or only mentions one, and nothing mechanical checks a verdict. A line misread as `mentions` skips a review the diff earned. What a reader audits is the per-line record in `trigger.txt` and `trigger-repair-<k>.txt`, each verdict with its reason, and the default that sends an unsettled line to `implements`. The session model reads with the worker's report in its context, and those two guards are what answer that bias.
- **The Step 4 trigger depends on a sibling being installed.** Step 4 runs `adversarial-review/scripts/match-triggers.py`, which reads `adversarial-review/references/trigger-table.md` at run time rather than a copy, so the rows stay current—and where `adversarial-review` is not installed there is neither script nor table. Step 0 checks for both files before its forecast and refuses the run by name where either is missing (row 100), so a run without the sibling stops before anything is built rather than guessing at a signal list.
- **Step 0's yes covers only the review it forecast, at the depth it forecast.** Step 0's red-team mode, which `RUN_DIR/redteam/mode.txt` records, is a forecast from the trigger match and the Depth table over the plan's owned paths. When Step 4's trigger fires over the real diff and the forecast did not, or `adversarial-review` derives a deeper depth than the forecast named, the review asks its own Step 2 question mid-run. That is deliberate, since the user never agreed to that review at that cost, but an unattended run stops there until someone answers. The forecast is approximate from the start: Step 0 has no diff to match, so it feeds the owned paths' current contents to `match-triggers.py` as an all-added diff against the empty tree (row 99), and the real diff can match more or fewer rows than the forecast counted. Every line of an existing file reads as added, so a small change to a large file forecasts the rows the whole file matches. An owned path that does not exist yet contributes nothing, so a file the plan creates is forecast from nothing, and a plan that only creates files forecasts `reproduce claims` whatever they will hold.
- **The herdr command lines are a cache.** Row 30 checks the flag names against `herdr worktree` and `herdr agent` help at run time, because the ones written down were true of one installed build. A renamed flag surfaces as a failed `herdr` call, and the fallback to `git worktree` plus a plain subagent covers it.
- **The in-scope test is judgment at the edges.** A finding inside the diff, naming a CRITERIA line, or naming a plan task is mechanically in scope, and everything else is a reading. The P0 tiebreak and the recorded ambiguity keep the call visible on the row; they do not make it mechanical.
- **A crashed step's last minutes go uncounted.** The close-first rule, and `budget`'s own close of an earlier step or a crashed `poll`, end a crashed interval at the newest stamp before the next `start` (row 102), which is the last thing the run recorded, not the moment it died. Work between that stamp and the crash counts toward nothing, so after a crash the budget reads low rather than high, and the stop fires later than it would have.
- **The budget stop fires only at the points that check it.** `phase_of` sees `review_over_budget` on a resume, and SKILL.md's **Timing** paragraph has the agent run `budget` before each review cycle within one invocation. A cycle the agent starts without running it goes unchecked until the next resume.
- **No scenario in EVALS.md has been run live yet**, so every claim this skill makes about behaving correctly end to end is [P] until somebody runs one.
- **The caller search is a grep, so a seam with a hidden caller reads as unexercised.** `git grep -n -w <symbol>` finds the callers that spell the symbol out. Dynamic dispatch, a string-keyed registry, reflection, and a call assembled from a constructed name all hide from it, and the verdict then reports `caller.path` null for a seam that production does exercise. `caller.search` carries the grep that decided it, so a reader who knows the codebase can see what it missed. Nothing in the step catches it for them.
- **The caller search returns more than callers.** Its only exclusions are test, spec, and fixture paths, so any document that spells the symbol out—a ledger row, an agent doc, a changelog—comes back as a hit; a search here for `paths_overlap` returns `AGENTS.md`, a README, and four ledger files beside the three scripts that call it. Row 86 says why the pathspec is not tightened. What it costs is that the reproducer reads every hit and decides, and a run that takes the first hit on faith reports a caller that calls nothing.
- **Nearest is judgment wherever more than one caller reaches the symbol directly.** The rule—the caller that calls the symbol itself, rather than something two hops out—is mechanical when one caller qualifies. Where several do, the tiebreak is the caller whose own input comes from furthest outside the seam, and judging that takes a reading of the codebase the search itself cannot make. `caller.path` is the entire record of the pick, so a reader who knows the code can see which caller was passed over; nothing in the step can tell them it was the wrong one.
- **D3's resolving-verb test is a heuristic, and it errs both ways.** Row 91 passes a sentence where a `settl…`, `resolv…`, or `answer…` word takes `open question` as its object, and the test cannot tell that verb from a negated one. "Nobody has settled this open question yet." exits 0 on a scratch plan. The other direction fires on a mention. A scratch plan whose line 7 is the wave-table cell `| T2 | the suite fails when open question is made unconditional |` fails with `check-plan: line 7: D3 open marker 'open question'`. The cell names the phrase and leaves nothing open. Backticks are the author's way out, since the scan skips a backtick span.
- **D3 reads list items under an open-state heading, never prose.** A paragraph under `## Open uncertainties` saying "Whether the threshold is right is unresolved." exits 0 on a scratch plan. Row 92's walk matches list items only, so an open item written as a sentence reaches the gate only if it uses one of the seven marker phrases.
- **The open-state heading test reads some topic headings as open and misses a label at the end.** `open questions` counts anywhere in a non-task heading, so `## Parsing open questions` over `- Reads the section.` exits 1 on a scratch plan. `unresolved` counts only at the start, so `## Items still unresolved` over an open item exits 0. A leading number has to sit outside the emphasis, so `## **3. Unresolved**` over an open item exits 0 as well. Row 92 says why each form got the scope it has.
- **The nesting test follows only part of CommonMark's list rules.** A paragraph ends the closed item's exemption only when it sits at or left of the item's marker, because a lazy continuation line can sit anywhere. After a blank line, CommonMark ends the item at any paragraph short of its content column. So `- ~~Old~~ done`, a blank, a paragraph one space in, a blank, and `  - Which cache backend` exits 0 on a scratch plan, where pandoc renders that last item as a new, open list. A tab counts as one column, and a marker followed by five or more spaces sets the content column too deep.
- **The heading walk does not know about fenced code.** D3 and D4 both read a `## Open questions` or `## Decisions` line inside a ```` ``` ```` block as a real heading. On scratch plans, an example list item inside a fence failed D3 and an example box failed D4, so a plan that shows the shape in a code block fails on its own example.
- **Emphasis inside the `open <noun>` phrase hides the state label.** `OPEN_STATE_HEADING_RE` needs `open`, whitespace, and the noun with nothing between them, so a `**` or `_` anywhere in the phrase breaks the match. On a scratch plan, `- Which cache backend to use` fails D3 under `## Open questions` and under `## **Unresolved**`, and exits 0 under `## **Open** questions`, `## _Open_ uncertainties`, and `## Open **decisions**`. D4 misses the underscore form too, because `D4_HEADING_RE` needs a word boundary before `open` and `_` counts as a word character. So under `## _Open_ uncertainties` an unchecked `- [ ] Which cache backend to use` also exits 0, where under `## Open questions` it fails with `check-plan: line 7: D4 unchecked box under heading 'Open questions'`. Round 3 of the review found this; the fix is queued on the pull request for a follow-up issue.
- **Nothing pins D3's loose-list case.** The `line.strip()` guard on `check_d3`'s paragraph clear keeps a blank line from ending a closed item's exemption. The shipped script passes a scratch plan with `- [x] Does the key include the branch?`, a blank, and `  - Yes, decided in review.` under `## Open items`. A scratch copy with `line.strip() and` deleted fails that plan with `check-plan: line 9: D3 unresolved item under heading 'Open items'`, yet `bash tests/work-issue-smoke.sh` in the same copy still prints `work-issue smoke: OK` and exits 0. The shipped behavior is right, but a regression would pass every test, and the missing pin is queued for the same follow-up.
- **A stop between the rebase and the `base_sha` rewrite waits on a human.** A rebase with no conflict that stops before Step 5 item 2 rewrites the file leaves no `conflict.txt`, so the probe reads `not-merge-base` and stops. The stop reason names the one-line fix. The window is the few commands between `git rebase` and the rewrite.
- **Row 7 can stop where a revert would have been safe.** `wave_unreported_committed` reads owned paths, not tasks, so a later wave that owns a path an earlier, committed wave also owned reads its half-written, unreported task as committed, and row 7 stops (row 116). The same holds for a reported task dirty on a path an earlier wave committed (row 117). That costs a human one look. The opposite error costs committed work.
- **On a run from before markers, an earlier wave's commit can stand in for a later task's gate.** Row 119's commit leg reads owned paths, not tasks, and it runs only where `RUN_DIR/gated/` is absent. On such a run, a later task that owns a path an earlier wave committed, and that failed without changing anything, counts, and row 8 skips its gate. divvy-up puts tasks that share a path in different waves, so any plan with a shared path can reach this on an old run. A run that writes markers never does. Row 116's stop has the same shape.
- **A wave that passed its gate and crashed before its commit is built twice.** Row 117 reads dirty owned paths as a gate that never ran, and Step 3 writes the `gated/` marker only after the commit lands, so nothing on disk records a pass that no commit followed. Row 7 reverts that work and re-dispatches it. That costs a worker's budget, not a commit.
- **A resume can start a second background loop.** Re-invoking the run while an earlier invocation's background poll is still alive starts another loop, and both write `poll-<k>` files and `poll` stamps into the same RUN_DIR. Nothing detects this, because a host normally kills a session's background tasks along with the session.
- **A stop with no quoted message costs up to two relaunches.** The driver can't recognize a stop whose row quotes nothing, such as a task that failed twice, so it relaunches until the no-progress halt fires (row 163). Each relaunch can redo work before reaching the same stop, such as a red-team round.
- **Two drivers on one issue are refused only under tmux.** `--detach` names the tmux session `work-issue-<N>`, and tmux refuses a duplicate. Under `nohup`, or with two drivers in the foreground, nothing stops the second one, and both relaunch agents into the same RUN_DIR.
- **A quoted stop message can match from the transcript.** Under an `--agent-cmd` that prints a verbose transcript, a stop message the agent quoted earlier in the run can land in the last 40 lines and be matched (row 162), and the driver halts or finishes on a stop the launch never reached.
- **A review naming a short SHA that a force push orphaned blocks adoption.** Row 168 refuses a named commit the clone can't resolve, and an orphaned commit can't be fetched by its short SHA, so adoption refuses until someone fetches the full commit.
- **Merging DEFAULT into an adopted branch stops the next resume.** The merge moves the branch's merge-base, so the probe reads the `base_sha mismatch (not-merge-base)` reason and stops until someone rewrites `base_sha` by hand. An adopted run never rewrites it, because it never rebases (row 170).
- **A second adopter with a different login posts a second deferred-findings comment.** Row 172 matches the comment by the pull request's author or the invoking login, and the first adopter's login is neither to the second one.
- **Step 0 item 6 doesn't prune `pr-<M>` directories.** Only row 1's cleanup offer moves an adopted run's directory to `closed/`.
