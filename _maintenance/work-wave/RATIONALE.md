# work-wave—rationale

Evidence tiers: **[E]** measured or observed in a real run, **[P]** practitioner reasoning from prior art, **[C]** convention inherited from this repo or its neighbors.

## Where This Came From

Five sources:

- **Issue #113 and the wave behind it** (kendrick/skills#113)—the four losses a hand-run wave paid: a schema coupling between two lanes with disjoint diffs, a merge test run after every branch was pushed, a CLI fact one lane learned and another relearned an hour later, and files handed back at worktree-relative paths, which cost two round trips, twice. It also supplied the six proposed behaviors and the three Non-Goals. It stops short at "an orchestrator remembering to ask", which is the pairwise coupling question with nothing to make anyone ask it.
- **#109's red-team round**, filed as rows 4 and 5 of the deferred-findings comment on PR #121—a `cp -R` scratch tree whose `.git` file pointed at the original gitdir, so its reproducer staged into the issue worktree's real index while believing it was sandboxed, and a `git archive` tree with no `.git`, which `check-waves.py`'s `repo_root_for` reads as no root and so skips every on-disk check. It stops short by filing both against `work-issue` and `divvy-up` and building nothing.
- **This repo's `work-issue`**—the lane itself. Its derived names, its RUN_DIR under the git common dir, its resume probe, its `--isolate` pin, and its confirmation, whose push half is answerable apart from its build half. It stops short at one issue. Its `check-inflight.py` skips a sibling whose plan has no `## Waves` table yet, and N lanes dispatched in one message open exactly that window.
- **This repo's `divvy-up`**—the disjointness proof run before dispatch, the three coupling shapes, the wave gate, and the rule that a failed task retries one rung up. It stops short at one working tree, where a directional coupling resolves as wave placement and a mutual one as a merged task. Neither exists across lanes.
- **agent-guild**, through the vendored chain `check-diff-scope.py` → `check-territories.py` → `check-waves.py` → `check-inflight.py`—`paths_overlap`, `owns_entry_problem`, and the table parser, with the #162 docstrings. It stops short at one tree per job.

## Known Limitations

- **The withheld grant is honored by the lane, not enforced by anything.** A lane that reads the build grant loosely publishes before the merge test. Step 5's route table stops the wave on a `build` report whose `pr` is non-null (row 19), and that is the only check that sees it. It sees the pull request after it opened, and a lane that opened one and reported `pr` as null passes it.
- **What `--isolate` does against the ask row is unverified.** The Step 3 collision check (row 17) keeps a pre-existing tree away from every unheld lane, so a wave never depends on the answer. A tree created at a lane's path between Step 3 and that lane's own Step 1 is outside the check. The already-started exemption (row 20) likewise rests on `work-issue`'s resume probe reading its own tree before the isolation table, and no live run has confirmed it.
- **The pre-dispatch footprint is a reading of `Files:` lines, not the lane's derived table.** A plan whose prose owns more than its `Files:` lines say passes Step 1 and fails the Step 5 re-check, after that lane has spent its build. Nothing catches it before the spend.
- **The Step 5 re-check compares tables, not diffs.** A lane that writes outside its own `## Waves` table and omits the path from `files_changed` passes the re-check. Its own `divvy-up` gate is the first thing that can catch it, and a Step 6 merge conflict is the last.
- **The contract-change trigger reads the lane's self-report.** Step 5 item 3 fires on a path in `files_changed` under CONTRACT_PATHS or on any path in `contract_changed`. A lane that changed a contract under a path neither field names reaches Step 6 without the early merge test.
- **The contract-change merge test waits for the changing lane's whole build.** Step 5 reads a lane's build report, and nothing fires before it arrives. The test reaches lanes still building only when the changing lane returns first. When it returns last, every other lane has already built against the old contract, and the break shows at Step 6.
- **The published SHAs are rebased SHAs that no merge test recorded.** Each lane branches from DEFAULT as it stood when the lane started. If DEFAULT moves at any point after that, before Step 6 or after it, each lane's rebase at `work-issue`'s Step 5 publishes a SHA that no `merge-test/<k>.md` names. What stands before publish is the tree-level test. Step 6 merges onto the current tip, and Step 7 re-runs it when the tip has moved since (row 31), so the combined tree those clean rebases produce was tested. A push to DEFAULT between Step 7's base check and a lane's own rebase escapes even that. The SHAs themselves are covered by Step 8's re-test at the published HEADs, which runs only after the pull requests are open.
- **An in-flight sibling that never writes a table blocks every wave.** Row 22 fails closed on it, and nothing in the skill tells a slow run from a dead one. The user decides, and moves a dead run to `closed/` by hand.
- **A red DEFAULT blocks publishing.** Step 6 proceeds only on green, and `references/merge-test.md` reads a later red at the baseline's failures as inherited. The inherited reading tells the user why, and nothing in the skill routes past it, so every wave on a red DEFAULT stops at Step 6 with nothing published.
- **The coupling question is judgment.** Five answers and two files make the call visible; they do not make it mechanical. A coupling the orchestrator misses gets `none` and surfaces, if at all, as a red merge test.
- **No scenario in EVALS.md has been run live yet**, so every claim this skill makes about behaving correctly end to end is [P] until somebody runs one.
