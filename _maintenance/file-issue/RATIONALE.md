# file-issue Skill Rationale

## Why This Skill Exists

Every issue-authoring tool on the market checks structure: did you fill the template, did you pass the gate. None of them check content: whether the reproduction actually runs, whether the acceptance criteria can fail, whether the scope has an edge. Structure compliance is cheap to verify and nearly worthless on its own, because a perfectly shaped issue with a prose gesture where the repro should be still costs a developer the same round trip.

That gap is the whole skill. The gates are content gates, and every one of them traces to a stated claim rather than to taste. Those claims are tiered, so a gate resting on convention rather than measurement says so out loud.

## Where the Evidence Comes From

[`_docs/file-issue-research.md`](../../_docs/file-issue-research.md) is the build input, a tiered survey ([E] measured, [P] practitioner, [C] convention) covering bug-report elements, duplicates, acceptance-criteria formats, titles, scope statements, agent-readiness, type taxonomies, interview burden, and templates. Its Rubric Derivation Table carries keep/cut verdicts per candidate item, and its Gaps Register was written as debt for this document. The rows below marked with a Q-number resolve into it.

The research also killed one feature and one statistic before either reached the skill. Both are recorded below.

## Decision Ledger

| Decision | Source | Reason |
| --- | --- | --- |
| Content gates, not structure compliance | local | Structure is what competitors already check. A well-shaped issue with an unrunnable repro passes every structure gate and still costs a round trip. |
| Named `file-issue`, not `create-issue` | local | "File an issue" is what people actually say, so it hits the auto-trigger surface more often. It also matches the research doc's filename. |
| Hard boundary against `to-tickets` in the description | local | `to-tickets` overlaps this trigger surface and does the opposite job of slicing a settled spec into many linked tickets. Without an explicit exclusion, one skill fires when the other was wanted. |
| No epic or tracking template | local | Multi-issue decomposition belongs to `to-tickets`, and its blocking-edges model is a better shape than epic-with-task-list anyway. Half-building it here would produce a worse version of something that exists. If it ever lands, it lands as edges. |
| Detection runs per invocation; no setup or config skill | local | mattpocock's run-once `setup-*` pattern assumes a repo you own and will configure. Consulting work happens in repos you saw for the first time this morning, so the ladder has to work cold or it does not work. |
| Duplicates surfaced, never blocked | Q2 | Evidence-contradicted, not merely unsupported. Duplicates rank 10% on developer severity, carry information the original lacks, and improve automatic triage when merged. Discarding them also teaches reporters to stop supplying follow-up detail. |
| Agent-readiness is a gate, and the differentiator | Q6 | The only evidence tying issue text directly to outcome: 38.3% of SWE-bench samples were flagged underspecified, and filtering them roughly doubled the measured resolve rate. What an agent needs beyond what a colleague needs is the verification command, the environment, and single-interpretation phrasing. |
| Verify the ready-for-agent label instead of applying it | local | `to-tickets` applies its label at publish. A label that is always applied carries no information; gating it on the rubric makes it mean something. |
| Acceptance criteria default to a checklist; GWT only on escalation | Q3 | No controlled study compares AC formats on ambiguity, testability, or defect rates. The silence is the finding. Falsifiability is what the evidence supports, so that is what gets gated and the notation stays style. |
| Elicit lives inline in `SKILL.md` | local | It runs on nearly every non-trivial invocation. Core-path logic behind a "go read file X" indirection is exactly the pattern that costs a run its coherence. Written to a stated interface contract so it stays liftable. The promotion path is to cut the section into its own file and add frontmatter, and the trigger is a second consumer (spec writing, workshop prep). Until then it stays put. |
| No runtime delegation to an external interrogation skill | local | The depth governor is the differentiator and `/grill-me` has none, because it is relentless by design. Injected steering competes with an already-loaded skill body and loses. And it would put a runtime dependency on an externally-maintained repo that a client machine may not have. Composition happens at the escape hatch instead, which is a clean sequential boundary. |
| Every question must name an empty slot | local | It makes the anti-annoyance promise checkable rather than aspirational. A question with no named gap is a question that should not have been asked. |
| Depth 1 caps at five questions | Q8, [C] | Calibrated from survey-length data, not measured on bug reporters: completion falls from ~83% at one to three questions to ~65% at four to eight, and the foundational bug-report survey was itself designed to a five-minute budget. |
| Templates in `assets/`, not `references/` | local | They are output material, and exactly one is read per run. Same split `inbox-to-memory` uses. |
| Detection always harvests; only Depth 2 probes code | local | The verification command and file pointers come from the repo, not from the user, so asking for them would burn questions on facts already on disk. Deeper source exploration is Depth 2's alone, because it costs real time and the skill's job is authoring an issue, not performing the engineering analysis. |
| The verification-command harvest is a ladder, not a single manifest lookup | local | The command is the most load-bearing harvest row—gate 6 refuses an agent-targeted issue without a runnable one—and a repo whose test surface is shell scripts has no manifest to read. Leaving that case to inference broke Step 1's mechanical promise on every such repo, this one included. The rungs stay judgment-free: manifest scripts, then runnable scripts under `tests/` or `scripts/`, then what CI runs, then an explicit `absent`. |
| Size check: ≥4 components, or the work does not fit one fresh context | local, uncalibrated | Deliberately loose, either condition alone fires, and a false escape is more annoying than a slightly oversized issue. The original third trigger, ≥7 acceptance criteria, was demoted to a smell: the same agent that writes the criteria decided whether the check fired, and eight criteria collapse to six on a rephrase, so the count measured the write-up rather than the work. Components and context fit are properties of the work—rewording merges no components and shrinks no reading list. Context fit is also the measure `to-tickets` sizes slices by, so the two skills agree at the boundary where one hands to the other. |
| Four types: bug, feature, task, spike | Q7 | Bug and feature are universal across GitHub, Linear, and Jira. Task absorbs chore and tech debt, matching Linear's "Chore", Jira's "Task". Spike is convention, kept for the reason below. |
| Spike kept despite not being vendor-canonical | Q7, [C] | Absent from Linear's fixed four and GitHub's defaults, but time-boxed research genuinely is a different shape of work with a different done-criterion. The template says so and tells you to file it as a task where the repo has no room for it. |
| Issue forms rank above Markdown templates | Q9 | Not taste. Across 100 projects and 1.9M+ issues, YAML forms specifically reduced time-to-resolution, reopenings, and discussion length relative to Markdown templates. |
| Preflight `gh auth status`, fail loud | local | A rendered draft looks like a filed issue. Silently degrading is how someone believes they reported a bug they did not report. |
| Creation only, never edit, close, or triage | local | Those are different jobs with different risk profiles. A skill that can close issues needs guards this one does not have. The one exception is linking the new issue to its parent and blockers, which admits exactly three kinds of write, each naming the new issue (#175): one `addSubIssue` for the parent, one `addBlockedBy` per blocker, and at most one `updateIssue` that removes only the entries whose link landed from the new issue's body. Nothing else in this skill edits an issue. |
| Parent and Blocked by link natively when they name an issue; anything else stays text | local, [C] | A prerequisite smuggled into a parenthetical sends an agent to run a file another ticket has yet to create, and a spec link left out throws away the cheapest context transfer there is, so every template carries both slots. The slots used to stay text to keep the skill creation-only. That cost showed when #142–#144 were filed: the maintainer stripped the text lines and set every link by hand with `addSubIssue` and `addBlockedBy`, because GitHub never reads a `#N` in a body as a relationship (#175). Now an entry that resolves to an issue node becomes a native link, and its text leaves the body only after its link has landed. Anything else stays as text: a spec path, a discussion or PR, a file the repo doesn't hold yet, or an issue the run can't resolve. Blocked by still states "None" outright on agent-targeted issues once its line is empty, because an absent list reads as unexamined rather than empty—the same absent-is-not-zero argument `inbox-to-memory` makes about its counts. Gate 6 is unchanged: an artifact named by the verification command or file pointers and missing from the repo has to appear on the Blocked by line, where it stays text because a path never resolves. The links cost the creation-only rule one exception, kept to three kinds of write naming the new issue: the two link mutations, one per link, and the one `updateIssue` that strips the linked entries. |
| For `link-issues.py link`, `--issue` is optional only under `--dry-run` | local | A dry run stops before `gh issue create`, so no issue exists yet to name. Without `--issue` the dry run looks nothing up, prints each mutation with a `<new>` placeholder, and sends nothing. Outside a dry run the new issue is the subject of both mutations, so `link` exits 3 when `--issue` is missing. Ruled by the orchestrator during #175. |
| A Parent held by another owner stays text and is never looked up | local, [P] | GitHub's add-sub-issue contract says the sub-issue must belong to the same repository owner as its parent (https://docs.github.com/en/rest/issues/sub-issues#add-sub-issue). A cross-owner parent that resolved would leave the body at creation and then fail the `addSubIssue` call, and the printed retry command could never succeed, so the provenance would be gone from both the body and the relationship. `resolve` treats such a parent as unresolved before any lookup, comparing owners case-insensitively because GitHub logins are. Blockers carry no such rule and still resolve across owners. Raised on PR #179 (discussion_r4213903046); the rejection itself is unverified live, so the row is [P] from the docs rather than [E]. |
| An entry the viewer cannot link stays text, decided at `resolve` from `viewerPermission` | local, [P] | Creating an issue needs read access, a dependency needs at least triage, and a sub-issue needs write (https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-an-issue, https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-issue-dependencies, https://docs.github.com/en/rest/issues/sub-issues). A filer who can create but not link would otherwise see the only Parent or Blocked by text leave the body and the mutation fail, with a retry that no permission change short of a grant can rescue. `resolve` reads `viewerPermission` once on the home repo for every blocker (`addBlockedBy` writes onto the new issue) and folds it into the parent's lookup query (`addSubIssue` writes onto the parent), and a level it cannot read counts as missing: a lost link costs one manual link later, and lost text costs the provenance. The cross-owner rule stays ahead of this check. Raised on PR #179 (discussion_r4222847237); the rejections are unverified live, so [P] from the docs. |
| Strip after link, never drop before create | local, [P] | The first cut dropped a resolved entry from the body before `gh issue create`, so the link that followed was the only record left. Three P0s on PR #179 each found a route by which that link then fails: a parent in another owner's repo, a filer without triage or write, and a GitHub Enterprise URL that `link` refuses. Patching each route left the next one lossy. Now every entry is filed as text, `link` records what landed, and `strip` removes exactly those entries in one `updateIssue`. A link that fails for any reason leaves its text where it was, and a strip that fails leaves both records, which is harmless. [P] because it reasons from the three failure routes rather than measuring anything. |
| The solo-repo cap scopes to the repo-shape trigger alone | local | Three of the five Depth 2 triggers are properties of the ask, one is a property of the workflow, and only one is a property of the tree. The unscoped cap let a solo repo talk an agent-destined, multi-component ask down to Depth 1, suppressing the code probe on exactly the issues that need file pointers, and it contradicted the floor-not-ceiling sentence directly above it. Scoping the cap keeps both rules rather than picking a winner. |
| Gate 6 requires verify-alone, with a declared blocker as the only exit | local, [P] | An issue scoped to one layer of a change passes every other gate and still cannot demonstrate itself: the agent finishes, cannot verify, and reports done regardless, which is the silent-wrong failure. Vertical slicing is `to-tickets`' central rule and practitioner consensus rather than a measured finding, so the evidence-map row carries [P]. The Depth 2 probe asks the prefactor question because it is already in the code when the question matters; sequencing prefactors into issues of their own stays with `to-tickets`. |
| Prose pass delegates to `technical-writing`; the interview still never delegates | local | The interview carries the depth governor, judgment this skill owns and loses the moment another skill runs it. The prose pass has no governor to lose—it is a mechanical audit, and where the sibling skill is missing the run degrades to shipping the draft unchanged, not to a broken one. `technical-writing` also owns the downstream prose-auditor invocation, so file-issue routes to one skill instead of two. |
| Feature and task questions front-load rule collisions | local, [C] | The bug ordering is measured and had no counterpart, so on feature asks the five-question ceiling went to whatever occurred to the interviewer first. Collisions between stated rules rank ahead of boundary gaps because a collision is a defect already in the ask—two rules that disagree on an input the feature must handle—while a boundary gap is merely unstated. Found by one real run (#23), never measured, so the evidence map carries it as [C]. |
| A derivation rule stated in the body is gated on a named falsifier | local, [C] | A ticket that introduces a derived value ships the rule for deriving it, and in prose that rule can key on the wrong thing and still read correctly — "invented when the governing field was null" names which field was absent, not which field the value traces to, and the two diverge outside the common case. The cost lands on every consumer at once: one provenance ticket produced four reclassifications in four modules, two review rounds that existed only to hunt them, and a coverage gap that survived five readings because the fixtures could not tell a right answer from a wrong one. Stated as a property the ruling is one task, testable before any classification code exists. The gate reaches the rule behind a derived value rather than every acceptance criterion, and asks for the falsifier rather than the test. Found by one real run (#110), never measured, so the evidence map carries it as [C]. |
| Gate 7's question sits outside every depth budget: asked at Depth 0, and outside Depth 1's five | local, [C] | Gates 1 through 6 can each be closed by revising the draft, so Step 6's "fix the draft" remedy always had somewhere to go. Gate 7 forecloses it deliberately, because inventing the falsifier is the thing the gate exists to prevent, so its only remedy is the question. That made Step 3's "Depth 0 asks nothing" a contradiction it had never been: Step 7 is the only step exempting Depth 0, so the gates run on a `--fast` draft. The alternative was to scope gate 7 to Depths 1 and 2, which was refused — it would make gate 7 the only depth-scoped content gate, and a fast draft is exactly where a derived rule stated in prose goes unchallenged, so scoping it out removes the gate from the case it was written for. The Depth 1 cap has the same shape and the same answer: five is the interview budget, and a gate failure is not an interview question. Asked and refused by one review round each; nothing measures what the extra question costs a capped run, so `[C]`. |
| The reconcile check treats the native field as the authority, and `DUPLICATE` never fails it | local, [P] | Row 41 made the native link the record for any Parent or Blocked by entry that names an issue (#175), so a body entry naming an issue is a leftover, and the native field decides whether it agrees. `_maintenance/file-issue/check-relationships.py` reports three classes. `UNLINKED` means the body names an issue the native field lacks, and `CONTRADICTED` means the body says `None` while the native field holds a link. Both put a reader on the wrong prerequisites, because an agent handed only the body starts work whose real blocker is still open. Reconciling #57–#62 by hand found four issues whose body named blockers the native field had never recorded, and #60 named three of them (#66). `DUPLICATE` means the body names an issue the native field already holds, so the two records agree and the line is only redundant. It prints but leaves the exit code at 0, because that hand reconciliation kept both records on purpose, and failing on them would fail the issues already fixed. [P] because it reasons from #66's drift table and #175's rule rather than measuring anything. |
| `check-relationships.py` lives under `_maintenance/` and imports `parse_entry` rather than copying it | local, [C] | A skill lands alone, so no installed skill may import from a sibling. `_maintenance/` is never installed. The script is a maintainer tool that runs from a clone of this repo, where `file-issue/scripts/link-issues.py` is always on disk, so it loads `parse_entry` with `importlib.util.spec_from_file_location` (the hyphen in the filename rules out a plain import) instead of vendoring it. A second definition of an issue reference would drift from the one `file-issue` resolves entries with, and the check would then disagree with the write path it audits. `_maintenance/jd/check-prose-refs.py` set the convention when it imported `jd-audit/scripts/validate.py` from a skill's own scripts directory, so [C]. |

## What the Research Removed

- **Blocking on suspected duplicates.** A plausible feature, cut because the evidence points the other way (Q2).
- **The "Gherkin catches 56% of requirements-phase defects" figure.** Circulates widely, has no primary citation, originates in vendor marketing. Explicitly excluded (Q3).
- **Resolution speed as a quality proxy.** Report quality and report lifetime are statistically independent, so a fast fix may just mean an urgent bug (Q1).
- **Severity and priority fields.** Zero developer importance. Collected when a detected template asks; never added (Q1).

## Deliberately Not Built

| Cut | Why |
| --- | --- |
| Editing the issue body after creation to add a failed link back as text | A failed link's text never left the body, so there is nothing to add back; the retry command `link-issues.py` prints under each failed link is the remedy. The one body write this skill makes is `strip`, which removes entries whose link landed and never adds a reference back; the only text it writes is the `None` an emptied agent-targeted Blocked by line gets, per row 41. Pinned by `refute_text` on `edit the body to add`, `add it back as text`, and `gh issue edit` in `tests/file-issue-smoke.sh`, with a `require_text` on the sentence that keeps `strip` to removal. |
| Text-only Parent and Blocked by for entries that name an issue | GitHub never reads a `#N` in a body as a relationship, so nothing that queries `subIssues` or `blockedBy` finds a text-only link. #142–#144 had to be linked by hand after filing (#175). The `refute_text` in `tests/file-issue-smoke.sh` pins the old Decision Ledger row's wording, so that row can't return. Quoting it here would trip the same refute. |
| Fixing findings automatically, by adding a link or stripping a body line | An `UNLINKED` finding has two possible causes with opposite fixes. Either nobody linked a real blocker, so the link gets added, or the body line went stale, so the line gets deleted. Only a person who knows the work can tell which, and `CONTRADICTED` splits the same way. A script that picked one fix would sometimes link a blocker that no longer blocks, or delete the only record of one that does. `jd-audit` stays report-only for the same reason. Pinned by `refute_text` on `addBlockedBy`, `addSubIssue`, and `updateIssue` over `_maintenance/file-issue/check-relationships.py` in `tests/file-issue-smoke.sh`. |

## Known Limitations

- **The size check is a first guess.** Nothing calibrates the ≥4-component threshold, and context fit is judged at drafting time rather than measured. Both need real use before they mean anything.
- **The derived-rule gate is all-types, but one template prompts for it.** Gate 7 is marked All types, while the drafting counterpart landed only in `feature.template.md`. Introducing a value is usually feature work and the templates are fallbacks used only where the repo has none, so the asymmetry is defensible — but a bug, task, or spike stating a derived rule first meets the gate at Step 6 with the body already written, which is the forced rewrite the prompt exists to prevent. Settled by a second real run where a non-feature ticket carries a derived rule.
- **Human evidence, agent-plausible.** Bettenburg, Ko, and Hooimeijer all predate LLM agents. SWE-bench echoes the core underspecification result, but the specific element rankings have not been validated against agent consumers.
- **Templates help, but not uniformly.** Presence correlates with faster resolution at effect size 0.59, yet some cohorts show reduced incoming volume and *longer* resolution after adoption. The net is positive and the mechanism is partly filtering. Do not overclaim it.
- **Open-source scope.** The bug-report findings explicitly disclaim transfer to closed-source projects, which have no patches and rarely surface stack traces. The skill's project-type conditionals on error output are the mitigation.
- **GitHub only.** Detection, creation, and duplicate search all assume `gh`. Linear and Jira would each need their own reference file and their own creation path. Left out until someone needs it.
- **No multi-issue path at all.** Deliberate, but it means a user who wanted decomposition gets a recommendation instead of a result. The escape hatch hands over the interview output so the work is not lost.
- **The permission gate reads the role, not the token.** `resolve` keeps an entry as text when `viewerPermission` is below what the link needs, and that field reports the viewer's role on the repo. A token scoped narrower than the role, such as a fine-grained token or a GitHub App installation granting issues read only, still gets a node, and its mutation fails. Since `strip` removes only entries whose link landed, the text stays in the body, so nothing is lost: the filer gets the `FAILED` line and its retry command, and the link waits on a broader token. No GraphQL field reports a token's scope for the script to check up front.
- **Linking is github.com-only.** `link` accepts only `github.com` issue URLs, so on a GitHub Enterprise checkout it exits 3 before sending anything and `strip` has nothing to remove. Every entry survives in the body as text, which is what stripping after the link buys. Native links on Enterprise would need the host read from `gh repo view` and the same write path, left for someone who runs one.
- **`strip` reads fenced code blocks only.** It skips slot lines inside ``` and ~~~ fences, closing a fence the CommonMark way, but two other Markdown rules are not modeled. A slot line in a 4-space indented code block is treated as a real one and stripped once its entry links; the relationship exists natively, so only the sample line changes. A backtick fence whose info string holds a backtick (```` ```a`b ````) is not a fence under CommonMark, but `strip` treats it as one and leaves the slot lines after it as text, a harmless duplicate. Templates never indent slot lines or open fences that way, and the red-team rounds on #179 found both by probing rather than in a real body.
- **The prose pass is a flat cost, not an opt-in one.** At Depth 1 and above on a machine with both skills installed, every run now pays a dispatch to `technical-writing` plus whatever auditor round trip that skill performs. If that proves annoying in practice, the fix is a future opt-out flag, not a weaker step.
